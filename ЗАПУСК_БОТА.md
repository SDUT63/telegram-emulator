# Запуск чат-бота СДУТ в MAX — полное руководство

Руководство для компьютера с Windows 10/11: бот и CRM работают на нём
же. Для Linux-сервера команды те же, отличаются пути (`.venv/bin/python`
вместо `.venv\Scripts\python.exe`) и автозапуск (`ops/systemd`).

Все команды проверены по коду ветки `max-bot-complete-2026`. Если
что-то в окне выглядит не так, как здесь описано, — раздел 11
«Неполадки».

---

## 1. Какой режим нужен

| Режим | Чем запускается | Где данные | Когда |
|---|---|---|---|
| **А. Пилот** | `Запустить-бота.bat` | файлы в папке бота (`data\sdut_bot.sqlite3`, `crm_data.json`) | сейчас; проверка бота на себе и первых людях |
| **Б. Боевой на компьютере** | `run_max_postgres.py` | PostgreSQL на этом же компьютере | когда нужны обращения с номерами, блок «Обращение» в CRM, контроль Д+7/Д+30, резервные копии |
| **В. Боевой на сервере** | `run_max_webhook.py` | PostgreSQL на сервере | когда будет сервер с доменом и HTTPS |

Режимы А и Б оба работают **без публичного адреса**: бот сам
спрашивает MAX о новых сообщениях (long polling). Белый IP, домен,
сертификат и открытые порты не нужны.

> **Важно.** Если в пилоте (режим А) уже есть анкеты реальных людей,
> не переключайте боевого бота на PostgreSQL, пока не готов перенос
> их данных (раздел 10). Иначе бот на PostgreSQL их «не узнает»:
> анкеты останутся в файлах пилота, а координатор их не увидит.

---

## 2. Что понадобится

1. **Python 3.13** — python.org/downloads. В первом окне установщика
   отметьте **«Add python.exe to PATH»**.
2. **Git for Windows** — git-scm.com. Нужен, чтобы забирать обновления,
   и для резервных копий (в нём есть Git Bash).
3. **PostgreSQL 16** — только для режимов Б и В. Установщик:
   postgresql.org/download/windows (EnterpriseDB).
4. **Токен бота MAX.** В MAX откройте `@MasterBot`, команда `/create`,
   скопируйте токен целиком.
5. **Второй, тестовый бот MAX** — тоже через `@MasterBot`. Им
   проверяют всё новое (раздел 7). Один токен нельзя обслуживать двумя
   программами одновременно: сообщения людей начнут случайно
   доставаться то одной, то другой.

Компьютер, на котором работает бот, не должен засыпать: Параметры →
Система → Питание → «Переводить в спящий режим» — **Никогда**.

## 3. Получить код

Один раз:

```powershell
cd C:\
git clone https://github.com/SDUT63/telegram-emulator.git sdut
cd sdut
git checkout max-bot-complete-2026
```

Папка бота — `C:\sdut`. Дальше все команды выполняются в ней.

Без Git: на GitHub выберите ветку `max-bot-complete-2026` → **Code** →
**Download ZIP**, распакуйте в `C:\sdut`. Обновлять так неудобно —
лучше через Git.

## 4. Режим А — пилот

### 4.1 Первый запуск

1. Дважды щёлкните **`Проверка.bat`**. В первый раз он создаст папку
   `.venv` и установит всё нужное (несколько минут, нужен интернет),
   затем проверит анкету, базу знаний и тексты согласия. В конце —
   «Проверка завершена успешно».
2. Дважды щёлкните **`Запустить-бота.bat`**. Если токена ещё нет, бот
   попросит вставить его одной строкой (символы на экране не видны —
   так и задумано) и сохранит в `token.txt`.
3. Напишите своему боту в MAX «привет». Должно прийти приветствие и
   просьба о согласии.

**Окно бота должно оставаться открытым.** Закрыли окно — бот
остановился. Остановить штатно — `Ctrl+C`.

### 4.2 Где лежат данные пилота

| Файл | Что в нём |
|---|---|
| `data\sdut_bot.sqlite3` | анкеты, переписка, согласия, журнал событий |
| `crm_data.json` | статусы, ответственные, заметки, контрольные звонки |
| `operators.json` | операторы CRM и их пароли (в виде хэшей) |
| `outbox\` | сообщения из CRM, ожидающие отправки |
| `token.txt` | токен бота |

Все эти файлы — **персональные данные или секреты**. В Git они не
попадают (`.gitignore`), но их нельзя пересылать, выкладывать или
оставлять в общей папке.

### 4.3 Если бот не подключается

Дважды щёлкните **`Связь-с-MAX.bat`**: он по шагам проверит интернет,
токен и доступ к MAX и скажет, что не так.

## 5. CRM — рабочее место координатора

### 5.1 Завести операторов

Без операторов войти в CRM некому. В папке бота:

```powershell
.venv\Scripts\python.exe crm_store.py
```

Программа спросит логин, имя и роль:

| Роль | Что может |
|---|---|
| 1 — оператор | ведёт обращения, статусы, заметки, сообщения человеку |
| 2 — старший | то же плюс отмена контрольного звонка |
| 3 — наблюдатель | только смотрит |

Пароль показывается на экране — запишите и передайте человеку лично.
Нужен хотя бы один старший. Повторный запуск с тем же логином меняет
пароль.

### 5.2 Открыть CRM

Дважды щёлкните **`Рабочее-место.bat`**, затем в браузере на этом же
компьютере: **http://localhost:5001**.

CRM нарочно слушает **только этот компьютер**. Открыть её с другого
компьютера или телефона без отдельного решения о защите нельзя: в
ней телефоны, адреса и сведения о здоровье.

**CRM должна смотреть в те же данные, что и бот.** Пилотный бот — CRM
из `Рабочее-место.bat`. Бот на PostgreSQL — CRM с теми же
настройками (раздел 6.6), иначе координатор увидит пустой список.

## 6. Режим Б — боевой на компьютере с PostgreSQL

### 6.1 Установить PostgreSQL

Запустите установщик PostgreSQL 16. Порт — **5432**. Запомните пароль
пользователя `postgres` — он понадобится один раз, ниже. Stack
Builder в конце можно не запускать.

### 6.2 Создать базу

Откройте PowerShell:

```powershell
& "C:\Program Files\PostgreSQL\16\bin\psql.exe" -U postgres
```

Введите пароль `postgres`, затем по одной строке (пароль базы
придумайте свой — **только латинские буквы и цифры**, не короче 16
символов; знаки `@ : / ?` в нём сломают адрес подключения):

```sql
CREATE ROLE sdut LOGIN PASSWORD 'ПридуманныйПароль16';
CREATE DATABASE sdut OWNER sdut;
\q
```

Для тестового контура (раздел 7) — ещё одна база:

```sql
CREATE DATABASE sdut_test OWNER sdut;
```

### 6.3 Файл настроек

Бот не читает `.env` — настройки передаются через переменные
окружения. Удобнее всего держать их в отдельном файле **вне папки
бота**, чтобы он никогда не попал в Git.

Создайте папку `C:\sdut-secrets` и в ней файл
**`C:\sdut-secrets\settings.bat`**. Пути к секретам и копиям —
латиницей: так их одинаково понимают и Windows, и Git Bash, и Python.

```bat
@echo off
rem Настройки боевого бота СДУТ. Не копировать, не пересылать.
set MAX_BOT_TOKEN=сюда-токен-боевого-бота
set SDUT_DATABASE_URL=postgresql://sdut:ПридуманныйПароль16@127.0.0.1:5432/sdut
set SDUT_ENV=production
set SDUT_BACKUP_PASSPHRASE_FILE=C:/sdut-secrets/backup-key.txt
set SDUT_BACKUP_DIR=D:/sdut-backups
set PYTHONIOENCODING=utf-8
set PYTHONUTF8=1
rem Срок хранения задаётся только после решения службы (Р5):
rem set SDUT_CASE_RETENTION_DAYS=365
```

В той же папке создайте **`backup-key.txt`** — одна строка, длинная
случайная фраза (40+ символов). Это ключ шифрования резервных копий:
**без него копии не расшифровать**. Храните его ещё и вне компьютера
(в сейфе, у руководителя), но не рядом с копиями.

Доступ к папке `C:\sdut-secrets`: правый щелчок → Свойства →
Безопасность — оставить только вашу учётную запись и «Система».

### 6.4 Подготовить базу

PowerShell в папке бота:

```powershell
cmd /c "C:\sdut-secrets\settings.bat && .venv\Scripts\python.exe scripts\migrate_postgres.py"
```

Создаёт таблицы. Запускать можно сколько угодно раз: уже применённое
пропускается. Если папки `.venv` ещё нет — сначала `Проверка.bat`.

### 6.5 Проверка готовности

```powershell
cmd /c "C:\sdut-secrets\settings.bat && .venv\Scripts\python.exe preflight.py"
```

Ответ — по каждой строке «ok», «!» (закрыть в ближайшие дни) или
«СТОП» (запускать нельзя), и итог. На свежей базе обычно три «СТОП»:

| Строка | Что сделать |
|---|---|
| Токен MAX | проверить, что в `settings.bat` токен скопирован целиком |
| Операторы CRM | завести операторов (раздел 5.1) |
| Резервные копии | создать `backup-key.txt` и указать путь в настройках |

И два «!», которые можно оставить: «Срок хранения анкет» (ждёт решения
службы, Р5) и «Доступ снаружи (TLS)» (нужен только для режима В).
Запускать боевого бота — когда «СТОП» не осталось.

### 6.6 Запуск бота и CRM

Создайте в папке бота два файла.

**`Бот-PostgreSQL.bat`**:

```bat
@echo off
chcp 65001 >nul
cd /d "%~dp0"
call "C:\sdut-secrets\settings.bat"
.venv\Scripts\python.exe run_max_postgres.py
```

**`CRM-PostgreSQL.bat`**:

```bat
@echo off
chcp 65001 >nul
cd /d "%~dp0"
call "C:\sdut-secrets\settings.bat"
.venv\Scripts\python.exe crm_server.py
```

В конце нет `pause` намеренно: эти же файлы запускает Планировщик
заданий (6.7), и после сбоя окно не должно ждать нажатия клавиши —
иначе автоматический перезапуск не сработает. Чтобы при ручном
запуске прочитать сообщение об ошибке, запускайте их из открытого
окна PowerShell: `.\Бот-PostgreSQL.bat`.

Запустите оба. Бот не стартует, если к базе не применены все
миграции, — это защита, а не поломка: выполните раздел 6.4.

CRM — снова **http://localhost:5001**. В карточке человека, дошедшего
до контрольной точки анкеты, появится блок **«Обращение»** с номером
`SDUT-ГГГГ-NNNNN`, статусом и кнопками следующего шага: взять, был
разговор, маршрут, направление исполнителю, начало помощи, итоги
контрольных звонков, закрытие.

**Пилот и боевой бот с одним токеном одновременно не запускать.**

### 6.7 Чтобы работало без вас

Планировщик заданий Windows → «Создать задачу»:

- **Общие:** «Выполнять для всех пользователей», «С наивысшими правами»
  не нужно.
- **Триггеры:** «При запуске».
- **Действия:** запуск `C:\sdut\Бот-PostgreSQL.bat`.
- **Параметры:** «При сбое перезапускать через 1 минуту», попыток — 999;
  снять «Останавливать задачу, если она выполняется дольше».

То же — второй задачей для `CRM-PostgreSQL.bat`.

Источник бесперебойного питания для этого компьютера — очень
желателен: внезапное выключение во время записи — худшее, что может
случиться с базой.

## 7. Тестовый контур — проверять всё новое

Перед любым обновлением и до боевого запуска режима Б — проверка на
отдельном боте и отдельной базе. Боевых людей это не касается.

1. Вторая копия кода: `git clone ... C:\sdut-тест` (раздел 3).
2. `C:\sdut-secrets\settings-test.bat` — как в 6.3, но **токен
   тестового бота** и база **`sdut_test`**.
3. В `C:\sdut-тест` — те же два bat-файла (6.6), но с
   `settings-test.bat`, и в CRM другой порт: добавьте в
   `settings-test.bat` строку `set CRM_PORT=5002`.
4. Миграции (6.4) и `preflight.py` (6.5) — с тестовыми настройками.

**Сценарий проверки** — пройти самому через тестового бота и CRM:

| # | Действие | Что должно получиться |
|---|---|---|
| 1 | Написать «мама не дышит» до согласия | сразу 103/112 и снова просьба о согласии; в карточке CRM нет пометки об угрозе жизни (до согласия ничего не сохраняется) |
| 2 | Дать согласие | блока «Обращение» в карточке ещё нет — черновик координатору не показывается |
| 3 | Ответить до контрольной точки | в CRM блок «Обращение» с номером, статус «Новое» |
| 4 | Закончить анкету | «Бот предлагает М…» с основанием |
| 5 | CRM: Взять обращение → Был разговор | статусы меняются |
| 6 | Подтвердить маршрут без основания | отказ: основание обязательно |
| 7 | Подтвердить с основанием → Направить исполнителю | нужен исполнитель в справочнике маршрутов |
| 8 | Помощь началась | статус «Контроль», задачи Д+7 и Д+30 со сроками |
| 9 | Записать итог Д+7 «Ждём начала» | просит дату следующего звонка |
| 10 | Продлить контроль → Закрыть «Помощь получена» | открытые задачи отменены |
| 11 | В боте: «заново» после закрытия | снова согласие; новое обращение — новый номер |
| 12 | В боте: «удалить» | данные стёрты, в CRM человека нет |
| 13 | Наблюдатель пытается закрыть обращение | «У вашей роли нет прав» |

Справочник исполнителей (для шага 7) — решение службы Р3; экрана для
него пока нет, запись заводится командой. В папке бота:

```powershell
cmd /c "C:\sdut-secrets\settings-test.bat && .venv\Scripts\python.exe"
```

и в открывшейся строке `>>>` по одной:

```python
from cases import CaseService
from cases_postgres import PostgresCaseRepository
s = CaseService(PostgresCaseRepository())
s.add_directory_entry(provider_key="kcson-avtozavod", route="М2",
    provider="КЦСОН Автозаводского района", available=True,
    phone="+7 (8482) 00-00-00", hours="пн–пт 8:00–17:00")
exit()
```

`provider_key` — постоянный латинский ключ исполнителя; `route` — М1…М5
или СМП. Если исполнитель сейчас не принимает (`available=False`),
обязательно `fallback="кому передать вместо него"`. Запись не
редактируется — новая версия заводится через `replace_directory_entry`
(история направлений не должна меняться задним числом).

## 8. Резервные копии (режим Б)

Копия делается скриптом `ops/backup_postgres.sh`: проверяет дамп,
шифрует его ключом из `backup-key.txt`, незашифрованный файл не
остаётся на диске даже на секунду. На Windows он запускается через
Git Bash.

**`C:\sdut\Резервная-копия.bat`**:

```bat
@echo off
cd /d "%~dp0"
call "C:\sdut-secrets\settings.bat"
set PATH=C:\Program Files\PostgreSQL\16\bin;%PATH%
"C:\Program Files\Git\bin\bash.exe" ops/backup_postgres.sh
```

Запустите вручную один раз — в `D:\sdut-backups` появится файл
`sdut_<дата>.dump.enc`. Затем Планировщик заданий: ежедневно, ночью.

Правила:

- копии хранятся **не на том же диске**, что база (лучше — ещё и вне
  компьютера: зашифрованный файл можно класть на внешний диск);
- старше 14 дней удаляются сами (`SDUT_BACKUP_RETENTION_DAYS`);
- **раз в квартал — пробное восстановление** в отдельную базу:
  `ops/restore_postgres.sh` с `SDUT_RESTORE_DATABASE_URL` на базу
  `sdut_restore` (скрипт откажется восстанавливать поверх рабочей).
  Копия, которую ни разу не восстанавливали, — не копия.

Пилот (режим А): остановить бота и скопировать `data\`,
`crm_data.json`, `operators.json` в зашифрованный архив (7-Zip,
AES-256, пароль не короче 16 символов).

## 9. Обслуживание

| Что | Как часто | Команда (с настройками, как в 6.4) |
|---|---|---|
| Проверка готовности | раз в неделю и после любого изменения | `preflight.py` |
| Воронка рекламы | по необходимости | `funnel.py` — где люди уходят; только числа, без имён |
| Выгрузка в Excel | по необходимости | `export_excel.py` |
| Чистка служебных записей об удалённых | раз в сутки | `ops\purge_privacy.py` |
| Чистка по сроку хранения | раз в сутки, **только после решения Р5** | `ops\purge_expired_cases.py` |

### Обновление кода

1. Сначала — на тестовом контуре (раздел 7).
2. Остановить бота и CRM (закрыть окна или остановить задачи).
3. Резервная копия (раздел 8).
4. `git pull` в папке бота.
5. `Проверка.bat` (доставит новые зависимости).
6. Миграции (6.4), затем `preflight.py` (6.5).
7. Запустить бота и CRM, написать боту «привет».

## 10. Переход с пилота на PostgreSQL

Бот на PostgreSQL ведёт обращения (номера, статусы, контроль), пилот —
нет. Чтобы люди из пилота не потерялись, их анкеты, переписку и
историю старой CRM надо перенести. Правила переноса согласовываются
(`docs/МОДЕЛЬ-ОБРАЩЕНИЯ-Р4-ПРОЕКТ.md`), программа переноса — после
утверждения.

До этого:

- **если в пилоте реальных людей не было** — можно начинать сразу с
  режима Б на пустой базе;
- **если были** — пилот работает как работал; режим Б — только на
  тестовом боте.

День переключения (когда перенос будет готов): остановить пилот →
дождаться, пока `outbox\` опустеет → архив файлов пилота (раздел 8) →
перенос с проверкой → `preflight.py` → запуск режима Б с **тем же**
боевым токеном → проверочное сообщение.

## 11. Неполадки

| Что видно | Причина | Что сделать |
|---|---|---|
| «На этом компьютере не найден Python» | Python не установлен или без PATH | переустановить с галочкой «Add python.exe to PATH» |
| Бот отвечает через раз или отвечают двое | один токен в двух программах | оставить одну: пилот **или** боевой |
| Бот не стартует: про миграции | база не подготовлена | раздел 6.4 |
| «run_max_postgres.py требует SDUT_DATABASE_URL» | запущен без файла настроек | запускать через `Бот-PostgreSQL.bat` |
| `connection refused` / база не отвечает | служба PostgreSQL остановлена | Службы Windows → `postgresql-x64-16` → Запустить; тип запуска — «Автоматически» |
| `password authentication failed` | пароль в адресе базы не тот | сверить с 6.2; спецсимволы в пароле не использовать |
| В CRM нет ни одного обращения | CRM смотрит не в те данные | CRM запускать тем же способом, что бот (5.2 / 6.6) |
| В CRM нет блока «Обращение» | CRM без PostgreSQL или человек не дошёл до контрольной точки | `CRM-PostgreSQL.bat`; черновики координатору не показываются |
| «Нужно войти» после перезапуска | удалён файл `.crm_secret` | войти заново |
| Русские буквы — вопросительные знаки | консоль не в UTF-8 | запускать через bat-файлы (в них `chcp 65001`) |
| Не подключается к MAX | сеть, токен, блокировка | `Связь-с-MAX.bat` |

## 12. Режим В — сервер с доменом (кратко)

Когда появится сервер с доменом: тот же PostgreSQL, бот —
`run_max_webhook.py` за обратным прокси с доверенным сертификатом
(`ops/tls/README.md`), автозапуск и копии — `ops/systemd`,
`ops/backup_postgres.sh`, восстановление — `ops/DISASTER_RECOVERY.md`.
Переменные — как в `.env.example`. Long polling и webhook для одного
бота одновременно не запускать.

## 13. Границы

Бот — навигатор: анкета → маршрут → передача координатору. Он не ставит
диагнозов и не является медицинской информационной системой. Вопросы
о согласии, сроках хранения, доступе к данным и шифровании диска
этого компьютера (BitLocker) — к ответственному за персональные данные.
