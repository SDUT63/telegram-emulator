## Термин: рабочее обращение

**Рабочее** — любой статус, кроме DRAFT и CLOSED. **Открытое** — любой,
кроме CLOSED (как в редакции 2, для И1).

Зачем: в редакции 2 «любой открытый» в 5.2 включал черновик, и отсюда
противоречие Г5. Черновик координатор не видит (5.1), номера у него
нет (4.9). Всё, что делает координатор, относится к рабочим
обращениям.

## Г5. Черновик не эскалируется и не объединяется

**Было (5.2):** «любой открытый → ESCALATED», «любой открытый →
CLOSED(duplicate)».
**Предлагаю:** «любое рабочее → ESCALATED», «любое рабочее →
CLOSED(duplicate)». Черновик закрывается только системой по сроку
(`abandoned_draft`).

| Что | Изменение |
|---|---|
| Переходы | убираются DRAFT → ESCALATED и DRAFT → CLOSED(duplicate) |
| Инварианты | без изменений; противоречие с И2 исчезает |
| Тесты | `test_г5_…` заменяется проверкой, что оба перехода запрещены |
| Код | `cases.allowed()`: общие правила только для рабочих статусов; ветка `ContractGap` для Г5 удаляется |

## Г1. Продление контроля — операция, не переход

**Было (5.2):** «CONTROL → CONTROL — контроль продлён: новая
контрольная задача с причиной». Вид задачи не определён.

**Предлагаю:** переход CONTROL → CONTROL убирается из таблицы 5.2.
Вместо него — операция «продлить контроль»:

1. Допускается только когда обращение в статусе CONTROL. Из
   ESCALATED — нет: сначала возврат от старшего.
2. Обязательны срок (с часовым поясом, не в прошлом) и причина
   (непустой текст).
3. Создаёт ровно одну задачу вида `control_extra`: статус `open`,
   исполнитель — ответственный по обращению — и ровно одно событие
   `control_extended` со сроком и причиной.
4. Повторное продление создаёт ещё одну самостоятельную задачу.
   Прежние задачи — `control_d7`, `control_d30`, прежние
   `control_extra` — не меняются.
5. Не меняет статус, `service_started_at`, вехи и существующие задачи.
6. `control_d7` и `control_d30` создаёт только вход в CONTROL (И8),
   эта операция их не создаёт. Ни одна задача не меняет вид.
7. Итоги `control_extra` — те же, что у контрольных звонков (4.6).
   «Ждём начала» и «исполнитель не пришёл» сразу требуют
   задачи-последствия — как на Д+7.
8. Число продлений не ограничено, пока служба не решит иначе.
9. Повтор того же нажатия в CRM отсекает идентификатор операции CRM
   (шаг 4), а не правило модели: каждое продление в модели — новое
   намерение.

| Что | Изменение |
|---|---|
| Переходы | CONTROL → CONTROL убирается |
| Инварианты | И8: «`control_d7`/`control_d30` — только при входе в CONTROL; `control_extra` — только операцией продления» |
| Тесты | `test_г1_…` заменяется на `test_продление_контроля_создаёт_дополнительную_задачу` (п. 1–7) и `test_повторное_продление_не_меняет_прежние_задачи` (п. 4–6) |
| Код | `TASK_KINDS`, `CONTROL_KINDS` + `control_extra`; `CaseService.extend_control()`; миграция 015 — CHECK `tasks.kind` |

**За службой:** ограничивать ли число продлений.

## Г2. Закрытие после разговора

**Было:** из CONTACTED закрыть нельзя. Если человек говорит «спасибо,
всё понял, помощь не нужна», координатор вынужден сначала подтвердить
маршрут.

**Предлагаю:**
- CONTACTED → CLOSED с причинами `consultation_enough`, `refused`,
  `solved_otherwise`, `not_eligible`;
- в контракт — уточнение: «разговор» — по телефону или в чате.
  Переписка с координатором в чате — тоже основание отметить CONTACTED;
- режим Б: новая причина `consent_not_given` — **только** CONTACTED →
  CLOSED(`consent_not_given`) и **только** при `legal_basis =
  vital_interest`. Смысл: обращение создано по угрозе жизни, с
  человеком связались, а согласия на обычную обработку он не дал.
  Действует, только если служба утвердит режим Б (Р10).

Других путей для режима Б не нужно: не ответил — NO_CONTACT →
CLOSED(`unable_to_contact`), как у всех; отказался письменно в чате —
координатор отмечает CONTACTED по переписке и закрывает с
`consent_not_given`. Вариант «NEW/ASSIGNED → CLOSED(`consent_not_given`)»
из первоначального предложения в документе шага 1 этим заменён.

| Что | Изменение |
|---|---|
| Переходы | + CONTACTED → CLOSED(4 причины); + CONTACTED → CLOSED(`consent_not_given`) для режима Б |
| Инварианты | И7: «`consent_not_given` — только у обращений с основанием `vital_interest` и только из CONTACTED» |
| Тесты | новые строки в таблице 5.2 тестов; `test_и7_отказ_от_согласия_только_в_режиме_б` — из CONTACTED при `vital_interest` можно; при `consent` и из NEW/ASSIGNED/NO_CONTACT нельзя |
| Код | `TRANSITIONS[CONTACTED]`, `CLOSE_REASONS_FROM[CONTACTED]`, проверка основания; миграция 015 — CHECK `close_reason` |

**За службой:** перечень причин закрытия после разговора.

## И16. Судьба открытых задач (Г4)

**Было:** задачи остаются открытыми, координатор отменяет вручную.
Отсюда «обращение закрыто, а звонок в плане» и два параллельных
контроля после повторного направления.

**Предлагаю — две автоматические отмены, обе в той же транзакции,
что и переход:**

| Причина отмены | Когда | Что отменяется |
|---|---|---|
| `case_closed` | любой переход в CLOSED, по любой причине | все задачи обращения в статусах `open` и `overdue` |
| `control_replaced` | переход CONTROL → REFERRED, ROUTE_CONFIRMED или WAITING_EXTERNAL | задачи `control_d7`, `control_d30`, `control_extra` в статусах `open` и `overdue`. Прочие, например `referral_followup`, остаются: они как раз про новое направление |

- На каждую отменённую задачу — событие `task_cancelled` с причиной.
- Эскалация и возврат задачи не трогают (И17).
- Следующий вход в CONTROL создаст новые Д+7/Д+30 — от новой даты
  начала помощи.
- Ручная отмена задачи координатором остаётся, с его причиной.

**И16.**
(а) У обращения в CLOSED нет задач в статусах `open` и `overdue`.
(б) Открытые задачи `control_d7`, `control_d30`, `control_extra` есть
только у обращения в CONTROL или в ESCALATED, пришедшего из CONTROL.
(в) Каждая автоматическая отмена — событие с причиной `case_closed`
или `control_replaced`.

**Атомарность.** Переход и отмена — одна транзакция: другой процесс
видит либо всё до, либо всё после. Состояния «обращение закрыто, а
задача открыта» не бывает даже на мгновение. Последний рубеж — в
базе: отложенный триггер при фиксации проверяет (а) и (б).

| Что | Изменение |
|---|---|
| Переходы | те же; меняются их последствия |
| Тесты | `test_и16_закрытие_отменяет_открытые_задачи` (в т. ч. `overdue`), `test_и16_новое_направление_отменяет_только_контроль`, `test_и16_эскалация_задачи_не_трогает`, `test_и16_база_не_даёт_закрыть_с_открытой_задачей` |
| Код | последствия в `CaseService.transition`; миграция 015 — отложенный триггер; `cases_memory.py` — та же проверка при фиксации |

## И17. Возврат от старшего меняет только статус

В шаге 1 возврат из ESCALATED заново запускал последствия перехода.
Ошибку поймали тесты до отправки, но в контракте правило не записано.

**И17.** Переход ESCALATED → S, где S — статус, из которого пришли:

| | |
|---|---|
| Меняется | только `status` := S и `status_before_escalation` := пусто |
| Добавляется | ровно одно событие `status_changed` |
| Не меняется | номер и счётчик номеров; вехи `opened_at` … `closed_at`; `suggested_route`, `final_route`, `route_changed_by`, `route_change_reason`; `assigned_to`, `priority`, `urgency`, `legal_basis` |
| Не создаётся | направлений, исходов, задач, снимков согласия, версий анкеты |

Вход в ESCALATED меняет только `status` и `status_before_escalation`,
причина обязательна, событие — одно.

Тест есть: `test_повторная_эскалация_ничего_не_дублирует` (Т2) — пять
эскалаций, после каждого возврата строка обращения совпадает с
прежней целиком. При переносе в код добавятся сверка числа исходов,
снимков согласия, версий анкеты и значения счётчика номеров.

## И18. После `ward_died` семье — ни одного автоматического сообщения

Отмены задач мало: сообщение могло уже стоять в очереди.

**Виды исходящих:**
- ответ бота на сообщение человека;
- сообщение координатора, написанное вручную;
- **автоматическое** — инициированное системой без входящего сообщения
  человека: напоминание, опрос, рассылка.

Сейчас автоматических сообщений нет вовсе. Правило — на будущее, чтобы
их нельзя было добавить без него.

**И18.**
(а) Переход в CLOSED(`ward_died`) в той же транзакции отменяет все
ещё не взятые на отправку автоматические сообщения этому человеку.
(б) После фиксации такого закрытия очередь не берёт на отправку ни
одного автоматического сообщения этому человеку.
(в) Сообщение, взятое на отправку раньше, перед самым вызовом MAX
перепроверяется под блокировкой своей строки; транзакция закрытия
отменяет сообщения под той же блокировкой. Итог: каждое
автоматическое сообщение либо отправлено до фиксации закрытия, либо
не отправлено вовсе. Отправленное до фиксации отозвать нельзя — это
честная граница.
(г) Ответы бота на сообщения самого человека и сообщения координатора
не запрещены: если родственник пишет, бот не должен молчать.
(д) Запрет снимается, только если человек сам начнёт новое обращение.

**Находка при сверке.** Для удаления данных сейчас есть только
проверка (б): `deleted_users` в `outbox_postgres.claim`. Перепроверки
(в) перед вызовом MAX нет: сообщение, взятое на отправку за миг до
удаления, уйдёт. Шаг 2 добавит её для обоих случаев сразу.

| Что | Изменение |
|---|---|
| Где | очередь исходящих; на шаге 2 у исходящего появятся вид (`reply` / `coordinator` / `automatic`) и ссылка на обращение |
| Тесты (шаг 2) | `test_и18_закрытие_отменяет_автоматические_в_очереди`; `test_и18_гонка_закрытия_и_отправки` — закрытие и отправка одновременно: сообщение либо ушло до фиксации, либо не ушло; `test_и18_ответ_на_сообщение_человека_не_запрещён`; та же гонка для удаления данных |
| Код (шаг 2) | `outbox_postgres.py`: вид сообщения, проверка при `claim`, перепроверка под блокировкой перед вызовом MAX — и для `ward_died`, и для удаления; миграция шага 2 |

|---|---|---|
| Ч1 | После удаления у человека остаётся только отметка | правило модели; окончательно — вместе с Р5 и юристом |
| Ч2 | Номер есть только у выходивших из черновика | вписать в 4.9 как правило |

| Ч6 | «→ CLOSED» без перечня — любая причина координатора | правило; определение — под таблицей 5.2 выше |

| Ч9 | Согласие — кнопкой в боте или на бумаге | **не правило, а юридический блокер запуска.** Для сведений о здоровье нужна письменная форма (п. 1 ч. 2 ст. 10 ФЗ-152); равна ли ей кнопка в боте (ст. 9) — решает юрист вместе с Р5. До его заключения `given_via` только записывает, как дано согласие; ни одна часть кода не делает вывода о юридической достаточности канала |

| Ч11 | Если бот маршрут не предлагал, координатор указывает причину своего | правило |
| Ч12 | Задачи Д+7/Д+30 назначаются ответственному | правило, и дополнение о смене ответственного — ниже |

**Ч12, смена ответственного.** Открытые задачи (`open`, `overdue`),
назначенные прежнему ответственному, переходят к новому:
- задача не пересоздаётся: у существующей меняется исполнитель;
- на каждую — событие `task_reassigned` с прежним и новым
  исполнителем;

## CI

Репозиторий `SDUT63/telegram-emulator` — форк. В форках GitHub не
запускает workflow по push и по расписанию, пока владелец не включит
их: все 9 прогонов в истории запущены вручную, еженедельный Security
Audit не запускался ни разу.

**Включить** (владелец, один раз): GitHub → репозиторий → вкладка
**Actions** → **«I understand my workflows, go ahead and enable
them»**.

**Проверить:** после включения — первая же отправка в рабочую ветку
должна дать прогон с событием `push`, не `workflow_dispatch`. Пока
такого прогона нет, CI считается ручным, и к каждому отчёту
прикладывается ссылка на ручной прогон этого коммита.
