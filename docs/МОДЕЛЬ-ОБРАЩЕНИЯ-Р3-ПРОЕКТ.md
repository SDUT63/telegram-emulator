## Новый термин: рабочее обращение

**Рабочее** — любой статус, кроме DRAFT и CLOSED. **Открытое** — любой,
кроме CLOSED (как в редакции 2, для И1).

Зачем: в редакции 2 «любой открытый» в 5.2 включал черновик, и отсюда
противоречие Г5. Черновик координатор не видит (5.1) и номера у него
нет (4.9). Всё, что делает координатор, относится к рабочим
обращениям.

## Г5. Черновик не эскалируется и не объединяется

**Было (5.2):** «любой открытый → ESCALATED», «любой открытый →
CLOSED(duplicate)».
**Предлагаю:** «любое рабочее → ESCALATED», «любое рабочее →
CLOSED(duplicate)». Черновик закрывается только системой по сроку
(`abandoned_draft`).

| Что | Изменение |
|---|---|
| Переходы | убираются DRAFT → ESCALATED и DRAFT → CLOSED(duplicate) |
| Инварианты | без изменений; противоречие с И2 исчезает |
| Тесты | `test_г5_…` заменяется проверкой, что оба перехода запрещены |
| Код | `cases.allowed()`: общие правила только для рабочих статусов; ветка `ContractGap` для Г5 удаляется |

Решение — логика модели, не служба.

## Г1. Продление контроля

**Было (5.2):** «CONTROL → CONTROL — контроль продлён: новая
контрольная задача с причиной». Вид задачи не определён, а
`control_d7`/`control_d30` считаются от начала помощи.

**Предлагаю:** продление — не переход статуса, а операция «продлить
контроль» в статусе CONTROL:
- новый вид задачи `control_extra`;
- срок называет координатор (до Р2 — календарная дата), причина
  обязательна;
- итоги — те же, что у контрольных звонков. «Ждём начала» и
  «исполнитель не пришёл» сразу создают задачу-последствие, как на Д+7;
- Д+7 и Д+30 по-прежнему создаёт только вход в CONTROL.

| Что | Изменение |
|---|---|
| Переходы | CONTROL → CONTROL убирается из таблицы 5.2 |
| Инварианты | И8: «Д+7/Д+30 — только при входе в CONTROL; `control_extra` — только операцией продления, со сроком и причиной» |
| Тесты | `test_г1_…` заменяется на `test_продление_контроля_создаёт_дополнительную_задачу`; таблица 5.2 в тестах — без CONTROL → CONTROL |
| Код | `cases.TASK_KINDS`, `CONTROL_KINDS` + `control_extra`; `CaseService.extend_control()`; миграция 015 — CHECK `tasks.kind` |

**За службой:** ограничивать ли число продлений. Без ответа — без
ограничения, каждое продление видно в истории.

## Г2. Закрытие после разговора

**Было:** из CONTACTED закрыть нельзя. Если человек говорит «спасибо,
всё понял, помощь не нужна», координатор вынужден сначала подтвердить
маршрут.

**Предлагаю:**
- CONTACTED → CLOSED с причинами `consultation_enough`, `refused`,
  `solved_otherwise`, `not_eligible`;
- в контракт — уточнение: «разговор» — по телефону или в чате.
  Переписка с координатором в чате — тоже основание отметить
  CONTACTED;
- режим Б: новая причина `consent_not_given` — CONTACTED →
  CLOSED(`consent_not_given`), только при `legal_basis =
  vital_interest`. Действует, только если служба утвердит режим Б (Р10).

| Что | Изменение |
|---|---|
| Переходы | + CONTACTED → CLOSED(4 причины); + CONTACTED → CLOSED(`consent_not_given`) для режима Б |
| Инварианты | И7: «`consent_not_given` — только у обращений с основанием `vital_interest`» |
| Тесты | новые строки в таблице 5.2 тестов; `test_и7_отказ_от_согласия_только_в_режиме_б` |
| Код | `TRANSITIONS[CONTACTED]`, `CLOSE_REASONS_FROM[CONTACTED]`, проверка основания; миграция 015 — CHECK `close_reason` |

**За службой:** перечень причин закрытия после разговора.

## Г3. Подопечный умер

**Было:** такой причины нет; придётся писать `refused` или
`solved_otherwise`, и отчёт службы будет неверен.

**Предлагаю:**
- причина `ward_died` — «человек, которому нужна была помощь, умер».
  Обращение о себе — тоже она;
- закрыть по ней можно из любого рабочего статуса, как дубликат;
- **после такого закрытия семье не уходит ни одного автоматического
  сообщения**: контрольные звонки отменяются (Г4), напоминаний и
  опросов нет. Только то, что координатор напишет сам. Это правило для
  шага 2 (бот) и очереди исходящих;
- данные хранятся по общим правилам закрытого обращения (Р5).

| Что | Изменение |
|---|---|
| Переходы | + любое рабочее → CLOSED(`ward_died`) |
| Инварианты | И7 — причина в перечне 5.3; И16 ниже отменяет задачи |
| Тесты | `test_смерть_подопечного_закрывает_из_любого_рабочего_статуса`; на шаге 2 — тест «после `ward_died` исходящих нет» |
| Код | `CLOSE_REASONS`, общее правило в `allowed()`; миграция 015 — CHECK |

**За службой:** формулировка в CRM и отчётах.

## Г4. Судьба открытых задач — новый инвариант И16

**Было:** задачи остаются открытыми, координатор отменяет вручную.
Отсюда «обращение закрыто, а звонок в плане» и два параллельных
контроля после повторного направления.

**Предлагаю:**
1. Закрытие обращения (любая причина) отменяет все его открытые задачи.
   Каждая отмена — событие с причиной `case_closed`.
2. Уход из CONTROL на REFERRED, ROUTE_CONFIRMED или WAITING_EXTERNAL
   отменяет открытые контрольные задачи (`control_d7`, `control_d30`,
   `control_extra`). Следующий вход в CONTROL создаст новые — от новой
   даты начала помощи. Прочие задачи, например `referral_followup`,
   остаются: они как раз про новое направление.
3. Эскалация и возврат задачи не трогают.

**И16.** У закрытого обращения нет открытых задач. Открытые
контрольные задачи есть только у обращения в CONTROL или
эскалированного из CONTROL.

| Что | Изменение |
|---|---|
| Переходы | те же; меняются их последствия |
| Инварианты | + И16 |
| Тесты | `test_и16_закрытие_отменяет_открытые_задачи`, `test_и16_новое_направление_отменяет_контроль` |
| Код | последствия в `CaseService.transition`; миграция 015 — отложенный триггер «у закрытого обращения нет открытых задач» |

## Новый инвариант И17: возврат от старшего меняет только статус

В шаге 1 возврат из ESCALATED заново запускал последствия перехода:
новый номер, второе направление, повторный контроль. Ошибку поймали
тесты до отправки, но правило в контракте не записано.

**И17.** Переход ESCALATED → статус, из которого пришли, меняет только
статус. Номер, маршрут, направления, задачи и вехи остаются как были;
каждая эскалация — отдельное событие.

Тест уже есть: `test_повторная_эскалация_ничего_не_дублирует` (Т2) —
пять эскалаций на этапах NEW, NEW, ASSIGNED, REFERRED, CONTROL.

## CI запускается только вручную — причина найдена

Репозиторий `SDUT63/telegram-emulator` — форк. В форках GitHub не
запускает workflow по push и по расписанию, пока владелец не включит
их. Поэтому за всю историю нет ни одного автоматического прогона —
даже еженедельного Security Audit.

**Как включить** (владелец, один раз): GitHub → репозиторий → вкладка
**Actions** → кнопка **«I understand my workflows, go ahead and enable
them»**. После этого каждая отправка в рабочую ветку запускает CI сам
(ветка уже есть в `ci.yml`). Правило «тесты проходят — только со
ссылкой на прогон этого коммита» остаётся.
