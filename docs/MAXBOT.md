# Чат-бот «Точка входа» для мессенджера MAX

Бот принимает обращение от человека, которому нужна помощь по уходу, или от того,
кто обращается в его интересах: собирает контактные сведения, проходит обязательный
фильтр экстренных состояний и передаёт карточку обращения координатору АНО «СДУТ».

Бот — это канал первичного обращения, а не служба помощи. Он не ставит диагнозов,
не определяет уровень нуждаемости, не обещает срок и объём чужой услуги и не называет
заявителю организацию-получателя: это делает координатор при звонке.

## Что бот собирает

Состав полей взят из перечня обязательных полей и чек-листа первичного обращения
методических рекомендаций АНО «СДУТ» (глава 13.1, приложение 4):

| Поле | Зачем |
| --- | --- |
| Дата и время обращения, канал | Расчёт срока, аналитика каналов |
| ФИО заявителя и телефон | Обратная связь и контрольный звонок |
| Кем приходится подопечному | Правомочность и адресат контроля |
| ФИО и возраст подопечного | Идентификация в профильной организации |
| Знает ли подопечный об обращении | Корректность контрольного звонка |
| Район и адрес | Выбор получателя по территории |
| Суть обращения со слов заявителя | Содержание маршрутного листа |
| Ограничения самообслуживания: передвижение, гигиена, питание | Разграничение М1 / М2 / М3 |
| Наличие и загруженность ухаживающего | Разграничение М2 и М3 |
| Боль или медицинский контроль на дому со слов заявителя | Признак М1 |
| Текущие социальные услуги, прошлые обращения | Данные по М2, история случая |
| Другие сферы: документы, транспорт, ТСР, опека, финансы | Признак М5 |
| Кто будет на связи и удобное время звонка | Контроль на 7-й день |
| Отметка STOP-1 / STOP-2 | Допуск в навигационный контур |
| Согласие на обработку персональных данных | Условие приёма обращения |

**Не собираются и не хранятся:** диагноз, назначения, медицинские документы, СНИЛС,
полис, паспортные данные, сведения о доходах, имуществе и составе семьи. Ни одно поле
такого рода не влияет на выбор маршрута, поэтому вопросов о них в анкете нет.

Согласие на передачу сведений конкретному получателю бот **не** собирает: одно согласие —
один получатель, а получатель известен только после решения о маршруте. Это согласие
оформляет координатор.

## Что бот решает, а что нет

Граница проведена так: **бот собирает факты, координатор принимает решение, эксперт устанавливает нуждаемость.**

Правила, по которым работает служба, вынесены из кода в отдельный версионируемый
файл `configs/policies.yaml`. Бот их только исполняет: он не содержит собственных
медицинских, социальных и юридических решений и не меняет их сам.

| Правило | Где задаётся | Пока не утверждено |
| --- | --- | --- |
| Перечень признаков STOP-1 | `policies.yaml → stop1` | линия закрыта, обращения не принимаются |
| Матрица маршрутов М1–М5 | `policies.yaml → routing` | направление не рассчитывается, координатор получает только признаки случая |
| Профиль собираемых данных | `policies.yaml → data_collection` | версия профиля указывается в каждой карточке |
| Формулировка согласия | `maxbot.yaml → consent.text` | применяется формулировка по умолчанию |
| Рабочий календарь и сроки | `maxbot.yaml → working_calendar`, `intake` | применяются значения по умолчанию |

Каждое правило имеет версию, дату и имя утвердившего. Версия перечня STOP-1 и
версия профиля данных записываются в карточку обращения: по ним видно, по каким
именно правилам принят случай.

## Фильтр STOP-1

Перед анкетой бот дословно задаёт вопросы из закрытого перечня признаков экстренного
состояния. При ответе «да» хотя бы на один вопрос:

1. анкета останавливается, бот называет номера 103 и 112;
2. фиксируются признак и время его выявления;
3. карточка немедленно уходит координатору с пометкой «STOP-1»;
4. у заявителя запрашиваются только имя и телефон — чтобы координатор перезвонил
   на следующий рабочий день.

Если ни один признак не выявлен, в карточке ставится отметка STOP-2 — формальный
допуск случая в навигацию.

Бот не является каналом экстренной помощи и прямо говорит об этом: при угрозе
жизни нужно звонить 103 или 112, а не писать в чат. Вопрос об уходе при этом
не закрывается — он возвращается в работу после стабилизации ситуации, для чего
создаётся отдельное действие координатора.

**Перечень признаков утверждает и подписывает заведующий отделением паллиативной
медицинской помощи.** Пока в `configs/policies.yaml` стоит `stop1.approved: false`,
бот не принимает обращения и отвечает, что приём не открыт, называя телефон службы
и номера экстренных служб. Список в файле — черновик для наладки; замените его
утверждённым, укажите версию, кто и когда подписал.

Каждый признак описывается четырьмя полями: `id`, `question` (задаётся дословно),
`trigger` (ответ, при котором признак считается выявленным) и `action`. Бот не
предполагает, что «да» всегда означает STOP-1: это определяет перечень.

## Предварительное направление

Матрица маршрутов задаётся правилами в `configs/policies.yaml`. Каждое правило
имеет идентификатор, приоритет, условия, маршрут и основание:

```yaml
- id: R040
  priority: 70
  conditions:
    lost_count: ">=3"
  route: "М3"
  reason: "значительная утрата самообслуживания по трём позициям"
```

Условия описывают признаки случая: `medical_need`, `caregiver`, `lost_count`,
`partial_count`, `limited_count`, `unknown_count`, `additional_spheres`,
`answers_complete`. Правила проверяются по убыванию приоритета, срабатывает первое
подходящее; в карточку попадают маршрут, идентификатор правила, основание и версия
матрицы. Менять методику можно, не трогая код.

Независимо от матрицы координатор всегда получает **признаки случая** — сколько
позиций самообслуживания утрачено, есть ли ухаживающий, что сказано о боли и
медицинском контроле, какие дополнительные сферы отмечены. Если матрица не
утверждена или ни одно правило не подошло, направление не рассчитывается, и
координатор решает по признакам.

Маршрут — подсказка, а не решение: уровень нуждаемости устанавливает эксперт,
маршрут определяет координатор. Заявителю направление не называется.

## Сроки и контрольные точки

Срок «один рабочий день» считается по рабочему календарю организации
(`working_calendar`), а не как «плюс 24 часа»: обращение вечером пятницы получает
срок не в субботу, а к концу ближайшего рабочего дня. Учитываются часовой пояс,
рабочие дни, рабочие часы и нерабочие праздничные дни.

После отправки обращения создаются три действия, которые хранятся в базе и
переживают перезапуск приложения:

| Действие | Срок |
| --- | --- |
| `initial_contact` — связаться с заявителем и оформить согласие на передачу | один рабочий день |
| `follow_up_7d` — контроль 7-го дня: началась ли помощь | 7 календарных дней, но не ранее истечения пятого рабочего дня |
| `follow_up_30d` — контроль 30-го дня: продолжается ли помощь | 30 календарных дней |

После STOP-1 создаётся действие `follow_up_after_emergency` — вернуться к вопросу
об уходе, когда ситуация стабилизируется.

Когда срок наступает, бот напоминает получателям карточек (интервал —
`intake.reminder_interval`, повторное напоминание не чаще раза в сутки).
Координатор смотрит открытые действия командой `/tasks` и закрывает их командой
`/done НОМЕР результат`; результат и автор записываются в журнал случая.

Это не полноценный workflow сопровождения: бот доводит контрольные точки до
координатора и фиксирует результат, но не заменяет систему ведения случая.

## Карточка координатора

После отправки анкеты карточка уходит в чат координаторов (`coordinator.chat_id`)
и/или в личные сообщения (`coordinator.user_ids`). В карточке: номер обращения, канал,
дата и время, отметка фильтра и версия перечня STOP-1, согласие, контакты, район и
адрес, суть со слов заявителя, ограничения, признаки случая, предварительное
направление с идентификатором правила и версией матрицы, версия профиля собираемых
данных и обязательное поле **«владелец следующего действия»** с датой.

При STOP-1 координатор получает два сообщения: короткое срочное оповещение сразу
при выявлении признака и карточку — когда заявитель оставит контакты.

## Доступ к сведениям об обращениях

Роли задаются в `maxbot.yaml → access`:

| Роль | Что доступно |
| --- | --- |
| `viewer` | карточка без контактов, адреса и текста обращения |
| `coordinator` | полная карточка, `/tasks`, `/done` |
| `supervisor` | то же, что координатор |
| `admin` | то же плюс настройка |

Каждый просмотр карточки записывается в журнал случая: кто, когда, в какой роли.
Полные карточки, телефоны и адреса не пишутся в журналы приложения — в логи
попадают номер обращения и факт передачи.

Файл базы и каталог создаются с правами `0600` и `0700`: доступ только у владельца
процесса.

## Запуск

1. Создайте бота в MAX через MasterBot и получите токен.
2. Скопируйте `configs/maxbot.yaml` и заполните: организация, телефон, районы,
   получатели карточек, утверждённый перечень STOP-1.
3. Узнайте идентификаторы координаторов: они пишут боту команду `/id`.
4. Запустите:

```bash
export MAXBOT_BOT_TOKEN="токен от MasterBot"
make maxbot-run          # или: go run ./cmd/maxbot
```

Сборка бинарного файла: `make maxbot-build` → `build/maxbot`.

### Режимы получения обновлений

* `bot.mode: polling` — long polling, ничего публиковать наружу не нужно. Подходит для
  запуска на любой машине и для наладки.
* `bot.mode: webhook` — бот подписывается на webhook и слушает `bot.webhook.listen`
  по пути `bot.webhook.path`. Нужен публичный HTTPS-адрес в `bot.webhook.url` и
  секрет `bot.webhook.secret` (MAX присылает его в заголовке `X-Max-Bot-Api-Secret`).

### Переменные окружения

Любой параметр конфигурации переопределяется переменной с префиксом `MAXBOT_`:
`MAXBOT_BOT_TOKEN`, `MAXBOT_BOT_MODE`, `MAXBOT_DATABASE_URL`, `MAXBOT_COORDINATOR_CHAT_ID`.
Токен в репозитории не хранится.

## Команды бота

Для заявителя: `/start`, `/apply`, `/my`, `/cancel`, `/help`, `/id`.

Для сотрудников службы: `/last` — последние обращения, `/card НОМЕР` — карточка,
`/tasks` — открытые действия по случаям, `/done НОМЕР результат` — закрыть действие.

Команда `/id` в групповом чате выводит идентификатор чата — его указывают
в `coordinator.chat_id`.

## Данные

Обращения хранятся в SQLite (`database.url`, по умолчанию `data/maxbot.db`):

| Таблица | Что хранит |
| --- | --- |
| `maxbot_applications` | карточки обращений |
| `maxbot_events` | журнал случая: начало анкеты, STOP-1, передача, просмотры карточки, закрытие действий |
| `maxbot_actions` | действия и контрольные точки 7-го и 30-го дня |
| `maxbot_daily_sequences` | дневные счётчики номеров обращений |
| `maxbot_processed_events` | отметки обработанных обновлений мессенджера |

Номер обращения выдаётся атомарно из дневного счётчика в транзакции: одновременные
обращения не получают одинаковый номер. Повторно доставленное обновление и повторное
нажатие кнопки не обрабатываются дважды.

Файл базы содержит персональные данные: храните его на защищённой машине,
ограничьте доступ и настройте резервное копирование по правилам организации.
SQLite подходит для пилота одной службы; для нескольких координаторов, аудита и
веб-интерфейса потребуется перенос на PostgreSQL — слой доступа к данным вынесен
в `internal/maxbot/storage` именно для этого.

## Тесты

```bash
make maxbot-test    # или: go test ./internal/maxbot/...
```

Тесты покрывают: прохождение анкеты целиком, протокол STOP-1 и ровно одно
оповещение координатора, повторно доставленные обновления, отказ от согласия,
пропуск неприменимых вопросов, проверку ответов, применение перечня STOP-1 и
матрицы маршрутов из policy, расчёт сроков по рабочему календарю (пятница, выходные,
праздники, граница рабочего дня), выдачу 100 номеров обращений параллельно,
создание и закрытие контрольных точек 7-го и 30-го дня, напоминания, роли доступа
и аудит просмотров, права на файл базы, восстановление анкеты после перезапуска.

## Структура кода

```
cmd/maxbot/main.go            запуск, polling или webhook, напоминания
internal/maxbot/config        конфигурация, роли и её проверка
internal/maxbot/policy        утверждаемые правила: STOP-1, матрица, профиль данных
internal/maxbot/calendar      рабочий календарь и сроки в рабочих днях
internal/maxbot/models        карточка обращения, действия, журнал
internal/maxbot/storage       хранилище на SQLite
internal/maxbot/survey        анкета: шаги, проверка ответов, признаки случая, карточка
internal/maxbot/bot           связь анкеты с MAX Bot API: команды, кнопки, контакты
```

Слои разделены: `policy` содержит правила и ничего не знает о мессенджере,
`calendar` считает сроки, `survey` ведёт анкету и не знает про MAX, `bot` общается
с MAX через интерфейс `Outbox`. Поэтому правила и анкета тестируются без сети.
