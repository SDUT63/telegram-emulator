# Модель обращения — проект редакции 4: перенос прежних данных

**Статус:** предложение. Контракт (`docs/МОДЕЛЬ-ОБРАЩЕНИЯ.md`) остаётся
в редакции 3 с решением Р10 (режим А); код переноса по этому документу
не пишется. Порядок тот же, что у редакции 3: служба утверждает →
изменения переносятся в контракт как редакция 4 → таблица соответствия
→ код и тесты → проверка на защищённой копии реальной базы → выпуск.

**Основа:** раздел 11 редакции 3; решения, согласованные при подготовке
(значение `legacy_no_result`, Д+7/Д+30 по `operator_calls.stage`,
раздельные «ответственный» и «кто выполнил», метка переноса); схема
базы — миграции 001–018 и код прежней CRM (`crm_postgres.py`,
`crm_server.py`) на коммите `20089ec` (merge PR #3).

**Принцип раздела 3, п. 5 не меняется:** чего тогда не сохранили, того
задним числом не выдумываем. Каждое правило ниже либо берёт значение
из конкретного поля, либо прямо говорит, что значения нет, и что
пишется вместо него — с отметкой происхождения в событии переноса.

## 1. Что лежит в прежних таблицах

Проверено по схеме и по коду, который эти таблицы пишет.

| Таблица | Что в ней | Как пишется | Что важно для переноса |
|---|---|---|---|
| `survey_state` | `user_id`, `state_json`, `updated_at` | бот, на каждое событие | **живая таблица**, а не прежняя: в ней разговор и состояние анкеты и после подключения обращений. В `state_json`: `consent` — `{at, version}` или `{refused}`; `started`, `finished`; `answers`, `alerts`, `acked`, `messages` (переписка), `step` |
| `operator_cases` | `status` ∈ {Новое, В работе, Закрыто}, `assigned` (пустая строка — никого), `created_at`, `updated_at` | создаётся **лениво**, первым действием оператора | у анкеты, которую никто не трогал, строки нет — её статус «Новое» по умолчанию |
| `operator_notes` | `who`, `text`, `system`, `created_at` | заметки оператора и системные: «Статус: …», «Взял в работу», «Контрольный звонок через N дней — сделан», «Отменен контрольный звонок…» | **единственная история** прежней CRM, в том числе время закрытия |
| `operator_calls` | `stage` ∈ {7, 30}, `who`, `created_at`; ключ `(user_id, stage)` | повторная отметка перезаписывает `who` и время, отмена (старший) удаляет строку | итога звонка нет; есть только «отмечен кем и когда» |
| `operator_operations` | идемпотентность сообщений оператора | внешний ключ на `operator_cases` | из-за этого ключа `operator_cases` нельзя сделать «только для чтения», пока ответы координатора его создают |
| `audit_events` | `user_id`, `event_type`, `event_json`, `created_at` (с часовым поясом) | бот, в транзакции события | по нему устанавливается часовой пояс прежних времён (П4) |

Времена в `state_json` (`consent.at`, `started`, `finished`) записаны
часами процесса бота **без часового пояса**. Часовой пояс сервера нигде
в установке не задан (`ops/systemd`, примеры окружения).

Отметки о подписанной бумажной форме согласия в прежних данных нет
нигде — ни в анкете, ни в CRM.

Данные пилота на ноутбуке (`crm_data.json` и файл анкет, режим Р6)
лежат вне PostgreSQL; разделом 11 они не покрыты (П12).

## 3. Изменения контракта, кроме раздела 11

**4.6, итоги контрольной задачи — добавить `legacy_no_result`:**
«Историческая отметка о выполнении контрольного звонка перенесена из
прежней CRM; итог звонка в исходных данных отсутствовал.» Три нормы:

1. Значение ставит только перенос. `complete_task` его отклоняет, то
   есть ни CRM, ни API координатора его не примут.
2. В списке итогов CRM его нет.
3. Для задачи с этим итогом задача-последствие не создаётся никогда
   (правило 4.6 о «ждём начала» и «исполнитель не пришёл» к ней
   неприменимо).

**И8 — добавить:** «…кроме задач, созданных переносом (раздел 11):
это история прежней CRM, а не вход в CONTROL; они всегда `done`».

**Новый инвариант И19 — перенос:** у каждого перенесённого обращения
ровно одно событие `migrated` с исходной строкой; повторный запуск
переноса ничего не меняет ни в одной таблице; перенос не создаёт
`suggested_route` и не вызывает правил модели, создающих задачи и
сообщения.

**Раздел 12 — новые вопросы:** Р14 (сообщения человеку о смене
статуса, П16); Р15 (часовой пояс, в котором работал боевой сервер, —
подтвердить найденное по данным, П4). Р6 дополняется вопросом П12.

## 4. Раздел 11 в редакции 4 — предлагаемый текст

### 11.1 Кто и как

Перенос — отдельная команда, а не миграция схемы. Два режима:
**проверка** (всё выполняется и откатывается, на выходе — отчёт) и
**перенос**. Один запуск за раз — общий замок. Каждый человек — своя
транзакция под тем же замком человека, что у бота и отправителя
очереди: сбой на одном человеке откатывает только его, попадает в
отчёт и делает код завершения ненулевым. Часовой пояс прежних времён —
обязательный параметр (П4).

**Предусловие:** в базе нет обращений, созданных не переносом (П10).
Иначе команда не начинает и называет их.

### 11.2 Кого

| Строка `survey_state` | Итог |
|---|---|
| `user_id` в `deleted_users` | пропуск |
| нет `consent.at` | обращения нет; `alerts` и `acked` стираются (Р10, режим А) |
| есть событие `migrated` у обращения этого человека | уже перенесено — ничего не меняется |
| иначе | человек + обращение + анкета версии 1 + снимок согласия + история прежней CRM |

Строка `operator_cases` без `survey_state` не переносится (П13).

### 11.3 Человек

`channel = max`, `channel_user_id = user_id`; `first_seen_at` — самая
ранняя запись этого человека в `audit_events`, если она есть, иначе
пусто.

### 11.4 Обращение

`source = bot`, `legal_basis = consent`, `created_at = started`
(если пусто — `consent.at`). Статус:

| Прежний статус (нет строки — «Новое») | Контрольная точка | Ответственный | Статус |
|---|---|---|---|
| Новое | не пройдена | нет | `DRAFT` |
| Новое / В работе | пройдена | нет | `NEW` |
| Новое / В работе | любая | есть | `ASSIGNED`, `assigned_to` из `operator_cases.assigned` |
| В работе | не пройдена | нет | `NEW` (П5) |
| Закрыто | любая | любой | `CLOSED`, `close_reason = migrated`, `closed_at` по П6 |

«Контрольная точка пройдена» — в `answers` есть ответ на вопрос
контрольной точки (тот же признак, что у моста).

**Номер** — у каждого обращения, кроме `DRAFT` и закрытых без
пройденной контрольной точки. Год — по `started` в местном времени
службы (Самара, UTC+4, как 4.9); внутри года — по `started`, затем по
`user_id`; счётчик года выставляется на последний выданный.
`opened_at = started` (П3).

### 11.5 Согласие

Снимок `processing`: `version` — из `consent.version`, `given_at` —
`consent.at`, `given_via = bot`, `text_hash` — пусто (текст на момент
согласия не сохранялся). Нет `consent.version` — человек не
переносится, строка в отчёте «аномалия». `medical_transfer` не
переносится ни у кого: отметки о подписанной форме в прежних данных
нет.

### 11.6 Анкета версии 1

`questionnaire_version = legacy`; `created_at = started`; `answers`,
`alerts` — как есть (П18); `completed_at = finished`;
`checkpoint_at` — пусто (П3); рассказа нет. Переписка (`messages`)
остаётся в `survey_state` — в модели обращения переписки нет.

### 11.7 Маршрут

`suggested_route` не заполняется (И13). Для законченной анкеты —
событие `route_reconstructed {route, also, signals, rules_version,
calculated_at}`: расчёт текущими правилами (`routing_rules.py`) в
момент переноса, с их версией. CRM подписывает его «восстановлено при
переносе»; в сравнение «бот предложил / координатор решил» такие
обращения не входят.

### 11.8 Заметки

Каждая строка `operator_notes` → событие `legacy_note {text, system}`
с её `who` и `created_at`, по порядку `id`. Системные заметки тоже:
это и есть история прежней CRM.

### 11.9 Контрольные звонки

| Поле задачи | Значение |
|---|---|
| `kind` | `stage = 7` → `control_d7`, `stage = 30` → `control_d30` |
| `status` | `done` |
| `due_at` | `finished`, иначе `started`, плюс `stage` календарных дней (П7) |
| `created_at` | та же база (`finished`, иначе `started`) |
| `done_at` | `operator_calls.created_at` |
| `done_by` | `operator_calls.who` — кто отметил звонок |
| `assigned_to` | `operator_cases.assigned`, пусто — если ответственного не было; `who` сюда не подставляется |
| `result` | `legacy_no_result` |

Отменённые звонки (строки нет) не переносятся — след отмены остаётся
в заметках. Задач-последствий нет. Правила модели, создающие задачи
при входе в CONTROL, не вызываются (И8 с исключением, И19).

### 11.10 Метка переноса

Последней записью в транзакции человека — событие `migrated`
(`who = system`): `{source: "survey_state", user_id, legacy_status,
legacy_assigned, opened_at_source, closed_at_source, tz_offset_minutes,
notes, calls, migration_version}`. Повторный запуск находит его и
ничего не делает (И19).

### 11.11 После переноса

- `operator_cases`, `operator_notes`, `operator_calls` — только для
  чтения: вставка и изменение запрещены триггером; удаление разрешено
  (удаление по просьбе и по сроку хранения).
- Ответы координатора не зависят от `operator_cases` (П14).
- CRM работает только с обращениями: прежние статусы, «Взять в
  работу» и прежние контрольные звонки уходят из карточки; список —
  по обращениям; выгрузка в Excel — по обращениям (раздел 13).
- Через один выпуск прежние таблицы удаляются отдельной миграцией —
  после проверки, что не осталось непереносённых строк, кроме П13.

### 11.12 Проверка на копии реальной базы

Отчёт до и после, по категориям из 11.2 и статусам из 11.4. Сверка:

- строк `survey_state` = перенесено + уже было + без согласия +
  удалённые + аномалии + ошибки;
- перенесённых обращений = снимков согласия = анкет версии 1 = событий
  `migrated`;
- строк `operator_notes` у перенесённых = событий `legacy_note`;
- строк `operator_calls` у перенесённых = задач с `legacy_no_result`;
- номера года идут без пропусков, счётчик = последнему;
- смещение часового пояса во всех парах П4 одно;
- второй запуск: ни одна таблица не изменилась (число строк и
  контрольная сумма содержимого).

## 5. Порядок выпуска

1. Проверка на копии реальной базы → отчёт → служба подтверждает
   числа и пояс (Р15).
2. Окно выпуска: бот и CRM остановлены.
3. Резервная копия (`ops/backup_postgres.sh`), проверка
   восстановления (`ops/restore_postgres.sh`) на стенде.
4. Миграции схемы выпуска, затем перенос в режиме «проверка», затем
   «перенос».
5. Сверка 11.12 на боевой базе; при расхождении — восстановление из
   копии, выпуск отменяется.
6. Запуск новой версии бота и CRM.
7. Следующий выпуск — удаление прежних таблиц.

Откат после запуска — только восстановлением из копии шага 3: события
обращений неизменяемы (И3), «вычитать» перенос из живой базы нельзя
без потери того, что успели сделать координаторы.
