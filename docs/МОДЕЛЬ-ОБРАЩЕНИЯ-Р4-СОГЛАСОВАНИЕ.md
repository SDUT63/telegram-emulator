# Лист согласования: проект редакции 4 — перенос прежних данных в обращения

**Что согласуется:** `docs/МОДЕЛЬ-ОБРАЩЕНИЯ-Р4-ПРОЕКТ.md` (PR #4).
**Цель:** зафиксировать решения службы до того, как будет написан код
переноса, чтобы по ходу разработки не принималось ни одного нового
решения.

Код переноса до утверждения не пишется. PR #4 содержит проект и два
исправления уже работающего кода (часть Ж) — они от этого листа не
зависят.

Ответ по каждому решению — одна строка внизу этого листа: «утверждено»,
«утверждено с замечанием: …» или факт, который требуется установить.

решения профильных специалистов.

## А. Не выдумывать историю

**Предлагается:** чего прежняя система не сохраняла, то при переносе не
восстанавливается как исторический факт: маршрут, время прохождения
контрольной точки, итог контрольного звонка, согласие на медицинскую
передачу. Вместо значения — отметка «в исходных данных нет».

**Единственное место, где проект ставит значение вместо отсутствующего
(П3):** время открытия обращения (`opened_at`) берётся равным началу
анкеты (`started`). Без него база не принимает номер обращения
(ограничение «номер есть тогда и только тогда, когда есть время
открытия»). Год и порядок номера раздел 11 уже определяет по `started`.
Источник значения записывается в событие переноса.

**Решение:** утвердить принцип и отдельно — правило П3.

---

## Б. Маршрут прежних обращений

**Предлагается:** исторического маршрута нет вообще — прежний бот его
не сохранял. Поле «бот предложил» (`suggested_route`) у перенесённых
обращений остаётся пустым. Для законченных анкет пишется событие
`route_reconstructed` — **расчёт текущими правилами в момент переноса**,
с версией правил. В CRM оно подписано «восстановлено при переносе» и в
сравнение «бот предложил / координатор решил» не входит.

**Решение:** утвердить.

---

## В. Прежние контрольные звонки

**Предлагается:**

| Поле задачи | Значение |
|---|---|
| вид | `stage = 7` → Д+7, `stage = 30` → Д+30 |
| статус | выполнена |
| итог | `legacy_no_result` — «отметка о звонке перенесена, итога звонка в прежних данных нет» |
| кто выполнил | кто отметил звонок в прежней CRM |
| ответственный | ответственный по обращению в прежней CRM; если не было — пусто (кто отметил, сюда не подставляется) |
| когда выполнена | время отметки |

`legacy_no_result` ставит только перенос; координатор не может его
выбрать ни в CRM, ни через API; задача-последствие для него не
создаётся никогда.

**Изменение против ранее обсуждавшегося (П7) — внимание:** срок
Д+7/Д+30 считается **не от даты поступления**, а так, как прежняя CRM
показывала его координаторам: от окончания анкеты, а если анкета не
закончена — от её начала. Иначе сроки перенесённых задач разойдутся
с тем, что видели люди.

**Решение:** утвердить, в том числе отдельно — правило срока П7.

---

## Г. Перенос не запускается при сомнении

**Предлагается:**

- каждое перенесённое обращение получает ровно одно событие `migrated`
  с исходной строкой; повторный запуск ничего не меняет (И19);
- перенос **отказывается начинать**, если в базе уже есть обращения,
  созданные не переносом (П10), и перечисляет их;
- перенос **отказывается начинать**, если часовой пояс прежних данных
  не установлен однозначно (Е);
- сбой на одном человеке откатывает только его и делает запуск
  неуспешным.

**Решение:** утвердить.

---

## Д. Сначала копия, потом бой

**Предлагается:** перенос на боевой базе без проверки на защищённой
копии запрещён. Порядок: резервная копия → восстановление на стенде →
перенос в режиме «проверка» → отчёт → повторный запуск (ничего не
меняется) → подтверждение отчёта службой → боевое окно.

**Состав копии:** `survey_state`, `operator_cases`, `operator_notes`,
`operator_calls`, `operator_operations`, `audit_events`,
`deleted_users`, **`persons`, `cases`** (без двух последних нельзя
проверить П10) и связанные с ними таблицы.

**Решение:** утвердить. Где хранится копия, кто к ней допущен и когда
она уничтожается — решает ответственный за персональные данные (И).

## Е. Часовой пояс прежних данных (Р15)

**Важно:** вопрос не в том, в каком поясе живёт служба. Прежний бот
писал времена часами операционной системы сервера, без пояса. Если
сервер — обычный арендованный или контейнерный, это почти наверняка
UTC, а не Самара. Гипотеза «UTC+4, потому что Тольятти» может оказаться
неверной ровно на четыре часа — и тогда сдвинутся номера на стыке
года, сроки Д+7/Д+30 и время закрытия.

**Предлагается:** начальной гипотезы не задавать. Пояс устанавливается
по данным: на копии берутся пары «время согласия в анкете» ↔ «время
события согласия в журнале `audit_events`» (там пояс записан); смещение
должно быть одним во всех парах. Найденное смещение подтверждает
ответственный за сервер и записывается в контракт строкой:
«прежние времена без пояса — время UTC±…». Если смещений несколько —
перенос не запускается, расхождения разбираются отдельно.

**Решение:** утвердить порядок; значение — после проверки на копии.

## Р6. Пилот на ноутбуке

**Нужен факт:** были ли в пилоте на ноутбуке (`crm_data.json`, файл
анкет) реальные обращения людей, которые нужно сохранить.

- Нет → данные пилота не переносятся, вопрос закрыт.
- Да → отдельное правило переноса этого источника (идентификация
  человека, согласие, анкета, история) — дополнением к проекту до
  начала кода. В текущий перенос такие данные молча не включаются.

До ответа данные пилота в перенос не включаются.

## П10. Принимает ли уже бот с обращениями события в бою

**Нужен факт, а не предположение:**

1. Принимала ли боевая версия с обращениями (PR #3) события: да / нет.
2. Если да — с какого момента.
3. Сколько обращений создано не переносом (запрос на копии:
   обращения без события `migrated`).
4. Чьи они: тестовые, сотрудников, реальных людей.

Ноль → П10 закрыт. Больше нуля → до кода переноса добавляется правило
сопоставления «прежняя история ↔ существующее обращение»; пропускать
таких людей нельзя — их прежняя история пропала бы вместе с прежними
таблицами.

## Р14. Что сообщать человеку и какими словами

**Предлагается минимальная безопасная модель до решения:** система не
отправляет человеку сообщений о переходах обращения, кроме прямо
утверждённых. `ward_died` — никаких сообщений никогда.

**Таблица для заполнения службой** (текст — дословно, с проверкой
ответственным за персональные данные):

| Событие | Сообщать? | Точный текст | Кто отправляет |
|---|---|---|---|
| обращение получило номер (принято) | | | система / координатор |
| назначен координатор | | | |
| состоялся разговор | | | |
| выбран маршрут | | | |
| передано исполнителю | | | |
| ждём исполнителя | | | |
| помощь началась | | | |
| назначен контрольный звонок | | | |
| контроль продлён | | | |
| обращение закрыто (кроме `ward_died`) | | | |
| `ward_died` | **нет** | — | — |
| смена ответственного | | | |

Отдельно: сообщение, которое система шлёт без входящего сообщения
человека, — **автоматическое** (9.1): оно привязывается к обращению и
отменяется при его закрытии (И18).

**Действующий риск — уже сейчас, до переноса.** В режиме PostgreSQL в
карточке CRM остались прежние кнопки статусов с отмеченной по
умолчанию галочкой «Сообщать человеку». Нажатие «Закрыто» отправляет:
«Ваше обращение закрыто… просто напишите сюда, анкета откроется
заново». С обращениями это неправда (новое обращение — только с новым
согласием, 7.6), и этот текст уйдёт семье в том числе после смерти
подопечного. Предлагается маленькой отдельной правкой до решения Р14:
не отправлять прежнее уведомление о закрытии (или хотя бы снять
галочку по умолчанию).

**Решение:** заполнить таблицу; отдельно — разрешить правку прежнего
уведомления о закрытии.

## И. Передать юристу / ответственному за персональные данные

- достаточность согласия и канала его получения (Р5, Ч9);
- сроки хранения обращений, анкет и копии базы (Р5);
- допустимость хранения перенесённых пометок о тревоге у людей,
  давших согласие позже (П18);
- доступ к защищённой копии, место хранения, уничтожение;
- формулировки сообщений человеку (Р14).

## Ж. Не требует решения службы

В PR #4 два исправления уже работающего кода, с тестами (на прежнем
коде тесты падают), CI зелёный:

1. **Чистка по срокам хранения** (`ops/purge_expired_cases.py`) после
   подключения обращений удаляла анкету, но оставляла обращение со
   снимком согласия и ответами навсегда, и не учитывала работу
   координатора по обращению. Срок остаётся один, из скрипта (Р5).
2. **Мост MAX → обращение** читал время анкеты без пояса как UTC; на
   сервере не в UTC время окончания анкеты сдвигалось.

Их можно влить, не дожидаясь согласования проекта, или вынести в
отдельный PR.
