## 3. Архитектурный принцип

Правильная целевая схема:

`MAX / Telegram / другие каналы`

→ `transport adapter`

→ `application services`

→ `Survey / Consent / Routing / Knowledge / Case`

→ `repository`

→ `PostgreSQL`

→ `operator CRM`

→ `передача в соответствующую медицинскую/социальную организацию`.

АНО «СДУТ» не должна превращаться этим проектом в самостоятельную медицинскую информационную систему или замену государственной МИС.

## 4. MAX

Текущий запуск через long polling оставить для разработки и тестирования.

Для production использовать существующий `max_webhook.py` и HTTPS Webhook.

Не допускать сценария, при котором production-запуск удаляет webhook перед стартом polling.

Сделать отдельные режимы:
- `dev`: polling;
- `stage`: webhook;
- `prod`: webhook.

Токен — только через environment/secret manager в production. `token.txt` оставить исключительно как локальный development fallback и исключить из Git.

## 5. Хранилище

Текущее JSON-хранилище допустимо для MVP и локального теста, но не для эксплуатации с персональными и потенциально медицинскими сведениями.

Целевой вариант — PostgreSQL.

Минимальные сущности:
- `users`;
- `cases`;
- `consents`;
- `survey_answers`;
- `survey_events`;
- `routes`;
- `alerts`;
- `messages`;
- `attachments`;
- `operators`;
- `audit_log`.

Не хранить всю историю кейса только как изменяемый JSON-объект.

## 6. Event/Audit trail

Добавить неизменяемый журнал событий:

- `CASE_CREATED`
- `CONSENT_GIVEN`
- `QUESTION_ANSWERED`
- `ALERT_TRIGGERED`
- `ROUTE_ASSIGNED`
- `OPERATOR_ASSIGNED`
- `CONTACT_ATTEMPTED`
- `CONTACT_SUCCESS`
- `CASE_CLOSED`
- `DATA_DELETED`

Это необходимо для воспроизводимости действий, расследования ошибок и контроля маршрутизации.

## 7. Идемпотентность

Текущая RAM-дедупликация событий — хорошая защита в рамках одного процесса, но после перезапуска она исчезает.

Для production сделать persistent idempotency:
- уникальный `event_id`/`message_id`;
- DB unique constraint;
- транзакционная обработка;
- при необходимости Redis для быстрого слоя дедупликации.

Повторная доставка одного события MAX не должна создавать второй кейс, вторую запись ответа или второе действие CRM.

## 8. Согласие и ПДн

Текущая версия согласия является хорошей UX-основой: есть версия согласия, фиксация времени и отдельная возможность прочитать полный текст.

Но перед production необходимо формализовать:
- какие ПДн собираются;
- для каких целей;
- правовое основание обработки;
- кто является оператором ПДн по каждому процессу;
- кому и при каких условиях передаются данные;
- сроки хранения;
- порядок удаления;
- резервные копии;
- технические журналы;
- права операторов CRM;
- разграничение доступа.

Формулировку вида «храним, пока не попросите удалить» не использовать как единственную политику хранения.

## 9. Клиническая безопасность

Бот не должен диагностировать.

Любая клинически значимая маршрутизация должна быть детерминированной и предварительно валидированной специалистами.

Разделить как минимум:

`STOP-103` → непосредственная угроза жизни → экстренная помощь;

`URGENT` → срочная связь с медицинским специалистом;

`PLANNED` → плановая маршрутизация ПМП/СДУ/социальной помощи;

`INFO` → информационный ответ.

LLM/AI не должен самостоятельно менять уровень срочности или принимать медицинское решение.

## 10. AI

Необязательный AI-модуль — архитектурно правильное решение.

AI допустим для:
- понимания свободного вопроса;
- поиска релевантной справочной информации;
- подготовки понятного информационного текста.

AI недопустим как единственный механизм:
- экстренной сортировки;
- постановки диагноза;
- определения медицинской тактики;
- назначения маршрута при критических симптомах.

## 11. CRM

Текущую CRM рассматривать как операторскую систему управления обращениями, а не как МИС.

Правильная цепочка:

`человек → бот → анкета → оператор → маршрут → профильная организация/служба`.

Не создавать дублирование государственной МИС без необходимости.

## 12. Транспортные адаптеры

Telegram не запускать копированием `max_bot.py`.

Сделать отдельный адаптер:

`transport/max.py`

`transport/telegram.py`

при общем application core.

Тогда один и тот же Survey Engine сможет работать через несколько каналов.

## 13. Рекомендуемая декомпозиция

Постепенно разделить крупные модули:

`max_bot.py` → транспорт + запуск;

`chatbot_survey.py` → core survey/domain;

`knowledge.py` → KnowledgeService;

`routing_rules.py` → RoutingService;

`crm_store.py` → repository;

`crm_server.py` → operator API/UI;

`consent.py` → ConsentService;

`case_service.py` → жизненный цикл обращения.

Не делать этот рефакторинг до стабилизации тестами.

Нельзя принимать изменения только потому, что бот «запустился».
