Хранилищ анкеты три (`storage.py`): файл — для разработки, SQLite —
пилот на ноутбуке, PostgreSQL — круглосуточная работа. CRM — две:
`crm_store.py` (JSON-файл) и `crm_postgres.py`; `crm_server.py`
выбирает по `SDUT_DATABASE_URL`.

Инфраструктурное ядро зрелое: транзакционная обработка событий,
надёжная очередь исходящих, вебхук, роли, журнал доступа, удаление
по просьбе. Слабое место — доменная модель: **человек = обращение**.

## 3. Принципы

1. **Человек ≠ обращение.** У человека может быть сколько угодно
   обращений; одновременно открыто — не больше одного на канал.
2. **История только дописывается.** Ничего не перезаписывается
   молча: новая версия анкеты, смена маршрута, смена статуса — это
   события с автором и временем.
3. **Бот предлагает, человек решает.** Маршрут, приоритет и
   подсказки из рассказа — предложения; итоговое решение принимает
   координатор и обязан указать причину, если не согласен с ботом.
4. **Всё, что посчитано по правилам, хранит версию правил и
   сигналы**, по которым посчитано. Через год должно быть видно,
   почему алгоритм решил именно так.
5. **Факт ≠ реконструкция.** То, что не было сохранено тогда, не
   записывается задним числом как сохранённое. Восстановленное по
   новым правилам помечается как восстановленное.
6. **Клиническая экстренность ≠ приоритет службы.** Первое — 103/112
   прямо сейчас; второе — как быстро служба обязана отреагировать.
7. **Согласие — снимок на обращении.** Человек соглашается на
   обработку ради конкретного обращения. Версия и объём согласия
   сохраняются на обращении и не меняются, когда меняется текст.
8. **Одна доменная логика, хранилища — адаптеры.** Правила переходов,
   сроков, нумерации и создания обращений живут в одном модуле.
   PostgreSQL, SQLite (если Р6) и память для тестов — реализации
   одного интерфейса без собственной бизнес-логики.
9. **Минимум ПД вне CRM.** В уведомлениях — номер, приоритет,
   район, срок. Подробности — только после входа в CRM.

## 4. Сущности

```
PERSON (кто пишет боту)
  └── CASE  SDUT-2026-00001 (номер — с перехода в NEW)
        ├── CONSENTS    снимок согласий, на которых держится обращение
        ├── INTAKE      версии анкеты + рассказ своими словами
        ├── TRIAGE      экстренность P0, приоритет P1–P3
        ├── ROUTING     предложенный → итоговый маршрут
        ├── TASKS       первый контакт, Д+7, Д+30, продления, эскалации
        ├── REFERRALS   куда направили (версия записи справочника)
        ├── OUTCOMES    что человек фактически получил
        └── EVENTS      вся история, только дописывается
```

### 4.1 Person

| Поле | Смысл |
|---|---|
| `person_id` | внутренний ключ |
| `channel` | `max` (позже `vk`, `telegram`, `web`, `phone`) |
| `channel_user_id` | `user_id` MAX; уникален в паре с `channel` |
| `first_seen_at` | когда впервые написал |
| `deleted_at` | отметка удаления по просьбе (сейчас `deleted_users`) |

Согласия у человека нет — оно на обращении (4.3). У человека только
отметка удаления: она не даёт запоздавшему событию MAX воскресить
стёртую карточку.

После удаления по просьбе у человека остаётся только эта отметка:
канал, идентификатор, время удаления (Ч1). Окончательно — вместе с
Р5 и юристом, включая то, как считать повторное обращение того же
человека.

Заявитель и подопечный — разные люди («о близком»: пишет дочь,
помощь нужна маме). В первой версии подопечный — часть intake
обращения (имя, возраст, адрес), а не отдельная сущность. Отдельный
реестр подопечных — после того, как цикл заработает (раздел 12, Р7).

### 4.3 Согласия обращения

| Поле | Смысл |
|---|---|
| `case_id` | обращение |
| `kind` | `processing` — обработка в боте и CRM; `medical_transfer` — передача в медицинскую организацию (отдельная форма 3, подписывается вне бота) |
| `version` | версия текста (`CONSENT_VERSION`, сейчас 1.0) |
| `text_hash` | хеш показанного текста — что именно видел человек |
| `given_at`, `given_via` | когда и как дано: кнопка в боте, бумага — запись факта (Ч9) |
| `withdrawn_at` | отзыв |

- Строка не изменяется, кроме однократной записи `withdrawn_at`.
- Новый текст согласия не меняет уже созданные снимки. Если юрист
  сочтёт изменение существенным для открытых обращений, бот
  переспрашивает — и это новая строка, а не правка старой.
- Отзыв `processing` — это «удалить»: стираются все обращения
  человека, как сейчас. Отзыв `medical_transfer` запрещает только
  передачу по этому обращению; само обращение продолжается.
- Срок хранения обращения считается по условиям того согласия,
  на котором оно держится (раздел 8).
- **Способ получения согласия определяется юридическим заключением
  по Р5.** До получения такого заключения код не оценивает
  юридическую достаточность канала получения согласия: `given_via`
  только записывает, как согласие дано (Ч9). Р5 — блокер запуска.

### 4.5 Справочник исполнителей

Маршрут без исполнителя — красивая, но неисполнимая рекомендация.

| Поле | Смысл |
|---|---|
| `directory_entry_id` | ключ **версии** записи; на него ссылаются направление и исход |
| `provider_key` | постоянный ключ организации через все версии — для отчётов |
| `route` | М1…М5, СМП |
| `provider` | организация (ТГКБ № 5, КЦСОН, …) |
| `phone`, `hours`, `address` | как связаться |
| `conditions`, `documents` | условия передачи и что нужно |
| `available` | исполнитель есть / нет |
| `fallback` | что делать, если `available = false` |
| `valid_from`, `valid_to` | период действия этой версии |

Запись не редактируется. Сменился телефон — у старой версии
проставляется `valid_to`, создаётся новая. Обращение, направленное
в сентябре, и через год показывает сентябрьский телефон и условия.

Пока исполнителя для М3 в Тольятти нет, запись М3 стоит
`available = false`, `fallback = «старшему координатору для ручной
маршрутизации»`, и CRM так и пишет, а не отправляет человека в
несуществующую точку.

### 4.6 Task

| Поле | Смысл |
|---|---|
| `task_id`, `case_id` | |
| `kind` | `first_contact`, `confirm_route`, `referral_followup`, `control_d7`, `control_d30`, `control_extra`, `escalation` |
| `due_at` | по рабочему календарю (раздел 6); до Р2 — календарные дни (Ч3) |
| `assigned_to` | при создании — ответственный по обращению (Ч12) |
| `status` | `open` / `done` / `cancelled` / `overdue`; открытая — `open` или `overdue` |
| `done_at`, `done_by`, `result` | итог; для контрольных (`control_d7`, `control_d30`, `control_extra`) — «помощь получена», «получена частично», «помощь идёт», «решилось иначе», «ждём начала», «исполнитель не пришёл», «отказ», «нет связи» |
| `escalated_at`, `escalated_to` | |

Итог задачи статус обращения не меняет: это данные для решения
координатора (раздел 5.2).

Итог «ждём начала» или «исполнитель не пришёл» на `control_d7` и на
`control_extra` не ждёт следующего звонка: в той же операции создаётся
задача-последствие `referral_followup` или `escalation`. Её вид и срок
до Р1/Р2 называет координатор (Ч4); потом — по регламенту и календарю.

Задачи отменяются автоматически при переходах (5.6, И16) или вручную
координатором — с его причиной.

**Смена ответственного (Ч12).** Открытые задачи, назначенные прежнему
ответственному, переходят к новому:
- задача не пересоздаётся: у существующей меняется исполнитель;
- на каждую — событие `task_reassigned` с прежним и новым
  исполнителем;
- срок не пересчитывается, просроченная остаётся просроченной;
- задачи, назначенные другому человеку (например, эскалация на
  старшего), не трогаются.

### 4.7 Referral и Outcome

**Referral:** `case_id`, `directory_entry_id`, `referred_at`,
`channel` (звонок, письмо, лично), `response`, `response_at`.

**Outcome** — цепочка «потребность → действие → исполнитель →
начало → результат»:

| Поле | Значения |
|---|---|
| `need` | паллиативная помощь, соцобслуживание на дому, уход/СДУ, ТСР, обучение родственника, оценка нуждаемости, документы, поддержка ухаживающего, другое |
| `action` | консультация, направление, сопровождение, выезд, выдача ТСР, обучение |
| `directory_entry_id` | версия записи справочника исполнителей |
| `service_started_at`, `service_received_at` | |
| `result` | `received` / `partially` / `waiting` / `refused` / `not_eligible` / `unable_to_contact` / `solved_otherwise` |

### 4.8 Case events

Каждое изменение — строка: `case_id`, `at`, `who` (оператор, бот,
система), `kind`, `payload` без лишних ПД. Строки только
дописываются. Это то, что сейчас разбросано по `operator_notes`
(системные записи) и `audit_events`.

Отмена, передача и продление задач — тоже события: `task_cancelled`
с причиной, `task_reassigned` с прежним и новым исполнителем,
`control_extended` со сроком и причиной.

### 4.9 Номер обращения

- Присваивается при переходе `DRAFT → NEW` (или при создании сразу
  в `NEW`: режим Б, обращение, заведённое оператором) — в той же
  транзакции, что и переход. Черновики номеров не получают: брошенная
  анкета не оставляет дыр, и последний номер года равен числу
  обращений, переданных координаторам.
- Номер есть ровно у тех обращений, что выходили из DRAFT. Черновик,
  закрытый без перехода в NEW, номера не получает (Ч2).
- Год — по местному времени Самары (UTC+4) в момент перехода:
  обращение, ставшее `NEW` 31 декабря в 23:30, получает номер
  уходящего года.
- Счётчик — таблица `case_number_counters (year PRIMARY KEY,
  last_value)`:

  ```sql
  INSERT INTO case_number_counters (year, last_value) VALUES (:year, 1)
  ON CONFLICT (year) DO UPDATE
      SET last_value = case_number_counters.last_value + 1
  RETURNING last_value;
  ```

  Строка года блокируется до конца транзакции: две одновременные
  транзакции получают номера по очереди, откат возвращает номер.
  Ни повторов, ни пропусков; новый год начинается сам. Транзакция
  перехода поэтому должна быть короткой — без сетевых вызовов внутри.
- Последний рубеж — `UNIQUE (number)`.
- Почему не `SEQUENCE`: последовательность на каждый год надо
  создавать заранее, а откат транзакции оставляет в ней пропуск.
- Формат `SDUT-{год}-{номер:05d}`; после 99 999 номер просто
  становится длиннее. Номер удалённого обращения не переиспользуется.
- В SQLite (если Р6 его оставит) — та же таблица: запись в SQLite и
  так идёт по одной (`BEGIN IMMEDIATE`).

## 5. Жизненный цикл

### 5.0 Открытое и рабочее обращение

- **Открытое** — в любом статусе, кроме CLOSED, включая DRAFT. Открытых
  обращений у человека не больше одного (И1).
- **Рабочее** — в любом статусе, кроме DRAFT и CLOSED. Всё, что делает
  координатор, относится к рабочим обращениям: черновик он не видит
  (5.1), номера у черновика нет (4.9).

Черновик не даёт завести второе обращение, но человек при этом не
застревает (Ч5): вернувшись, он продолжает свою анкету с места
остановки; «заново» даёт новую версию анкеты (раздел 7, п. 5); через
30 дней черновик закрывается, и следующий вход начинает новое
обращение. Нужна срочность — тревога P0 при известном телефоне или
просьба перезвонить сразу переводят черновик в NEW.

### 5.1 Статусы

| Статус | Значение | Кто переводит |
|---|---|---|
| `DRAFT` | согласие дано, анкета не дошла до контрольной точки; в очереди CRM не видно | бот |
| `NEW` | обращение готово к работе, есть номер | бот / оператор |
| `ASSIGNED` | есть ответственный | оператор / автоматически |
| `CONTACTED` | состоялся разговор с человеком — по телефону или в чате; переписка с координатором в чате тоже основание | оператор |
| `ROUTE_CONFIRMED` | итоговый маршрут выбран | оператор |
| `REFERRED` | передано исполнителю | оператор |
| `SERVICE_STARTED` | помощь фактически началась | оператор |
| `CONTROL` | идут контрольные звонки Д+7/Д+30 и продления (5.5) | система |
| `CLOSED` | закрыто с причиной | оператор; система — только черновик по сроку |

Ветки, из которых возвращаются в основной поток:
`NO_CONTACT` (N попыток без ответа), `WAITING_EXTERNAL` (ждём
исполнителя), `ESCALATED` (у старшего).

### 5.2 Переходы

```
DRAFT → NEW                    контрольная точка пройдена, или тревога P0 при известном телефоне,
                               или человек просит перезвонить; номер — здесь
DRAFT → CLOSED(abandoned_draft) единственное автоматическое закрытие: 30 дней без перехода в NEW
NEW → ASSIGNED                 назначен ответственный
ASSIGNED → CONTACTED | NO_CONTACT
NO_CONTACT → CONTACTED | CLOSED(unable_to_contact)
CONTACTED → ROUTE_CONFIRMED
CONTACTED → CLOSED(consultation_enough / refused / solved_otherwise / not_eligible)
CONTACTED → CLOSED(consent_not_given) — только при legal_basis = vital_interest
ROUTE_CONFIRMED → REFERRED | CLOSED(consultation_enough)
REFERRED → SERVICE_STARTED | WAITING_EXTERNAL | CLOSED(refused / not_eligible)
WAITING_EXTERNAL → SERVICE_STARTED | CLOSED(любая причина координатора)
SERVICE_STARTED → CONTROL      создаются задачи Д+7 и Д+30
CONTROL → CLOSED(любая причина координатора)
CONTROL → REFERRED             исполнитель не пришёл или нужен другой — новое направление
CONTROL → ROUTE_CONFIRMED      нужен другой маршрут — новый итоговый маршрут с причиной
CONTROL → WAITING_EXTERNAL     помощь обещана, но не началась
                               при уходе из CONTROL контроль отменяется: control_replaced (5.6)
                               продление контроля — операция, не переход (5.5)
любое рабочее → ESCALATED      просрочка или решение старшего
ESCALATED → статус, из которого пришли — меняется только статус (5.7)
любое рабочее → CLOSED(duplicate) со ссылкой на основное обращение
любое рабочее → CLOSED(ward_died)
любой переход в CLOSED         открытые задачи отменяются: case_closed (5.6)
```

«Любая причина координатора» — все причины 5.3, кроме системных
(`abandoned_draft`, `migrated`), `duplicate` и `consent_not_given`
(Ч6). Переход DRAFT → NEW — только по одному из трёх оснований первой
строки (Ч7). Черновик не эскалируется и не закрывается как дубликат:
общие правила действуют только для рабочих обращений (5.0).

Запрещённый переход отклоняется, а не выполняется «как получится».

**Контроль — это задачи, а не автомат.** Итог контрольной задачи
статус не меняет (И8). Что делать с обращением дальше — закрыть,
направить заново, ждать — решает координатор переходом из таблицы;
продлить контроль — операцией 5.5. Итог «исполнитель не пришёл» или
«ждём начала» на Д+7 и на продлении не ждёт следующего звонка (4.6).

### 5.3 Причины закрытия

`help_received`, `help_partial`, `solved_otherwise`,
`consultation_enough`, `refused`, `not_eligible`,
`unable_to_contact`, `duplicate`, `abandoned_draft`, `migrated`,
`consent_not_given`, `ward_died`.

- **`consent_not_given`** — только у обращения режима Б
  (`legal_basis = vital_interest`) и только из CONTACTED: обращение
  создано по угрозе жизни, с человеком связались, а согласия на
  обычную обработку он не дал. Не ответил — NO_CONTACT →
  CLOSED(`unable_to_contact`), как у всех; отказался письменно в чате —
  координатор отмечает CONTACTED по переписке. Действует, только если
  служба утвердит режим Б (Р10).
- **`ward_died`** — человек, которому нужна была помощь, умер; в том
  числе при обращении о себе. Это **самостоятельная причина закрытия,
  а не разновидность `duplicate`**: общее у них только правило
  перехода — обе разрешают переход «рабочее → CLOSED(причина)».
  Семантически они не объединяются. Имя в коде техническое;
  формулировку в CRM и отчётах выбирает служба (Р13). Данные хранятся
  по общим правилам закрытого обращения (раздел 8, Р5). После такого
  закрытия действует И18 (9.1).

Удаление по просьбе человека — не закрытие: обращение стирается
целиком, остаётся только обезличенный счётчик удалений.

### 5.4 От чего считать Д+7 и Д+30

От `service_started_at`: контроль проверяет получение помощи, а не
сам факт обращения. Если помощь так и не началась, а обращение
закрывают, Д+7/Д+30 не создаются — вместо них причина закрытия.
Повторный вход в CONTROL создаёт новые Д+7/Д+30 — от новой даты
начала помощи; прежний контроль к этому моменту отменён (5.6).

### 5.5 Продление контроля

Продление — операция, а не переход статуса:

1. Допускается только когда обращение в статусе CONTROL. Из
   ESCALATED — нет: сначала возврат от старшего.
2. Обязательны срок (с часовым поясом, не в прошлом) и причина
   (непустой текст).
3. Создаёт ровно одну задачу вида `control_extra`: статус `open`,
   исполнитель — ответственный по обращению — и ровно одно событие
   `control_extended` со сроком и причиной.
4. Повторное продление создаёт ещё одну самостоятельную задачу.
   Прежние задачи — `control_d7`, `control_d30`, прежние
   `control_extra` — не меняются.
5. Не меняет статус, `service_started_at`, вехи и существующие задачи.
6. `control_d7` и `control_d30` создаёт только вход в CONTROL (И8),
   эта операция их не создаёт. Ни одна задача не меняет вид.
7. Итоги `control_extra` — те же, что у контрольных звонков (4.6).
   «Ждём начала» и «исполнитель не пришёл» сразу требуют
   задачи-последствия — как на Д+7.
8. Число продлений не ограничено, пока служба не решит иначе (Р11).
9. Повтор того же нажатия в CRM отсекает идентификатор операции CRM
   (шаг 4), а не правило модели: каждое продление в модели — новое
   намерение.

### 5.6 Задачи при переходах (И16)

Две автоматические отмены, обе в той же транзакции, что и переход:

| Причина отмены | Когда | Что отменяется |
|---|---|---|
| `case_closed` | любой переход в CLOSED, по любой причине | все задачи обращения в статусах `open` и `overdue` |
| `control_replaced` | переход CONTROL → REFERRED, ROUTE_CONFIRMED или WAITING_EXTERNAL | задачи `control_d7`, `control_d30`, `control_extra` в статусах `open` и `overdue`. Прочие, например `referral_followup`, остаются: они как раз про новое направление |

- На каждую отменённую задачу — событие `task_cancelled` с причиной.
- Эскалация и возврат задачи не трогают (5.7).
- Следующий вход в CONTROL создаст новые Д+7/Д+30 — от новой даты
  начала помощи.
- Ручная отмена задачи координатором остаётся, с его причиной.

**Атомарность.** Переход и отмена — одна транзакция: другой процесс
видит либо всё до, либо всё после. Состояния «обращение закрыто, а
задача открыта» не бывает даже на мгновение. Последний рубеж — в
базе: отложенный триггер при фиксации проверяет И16 (а) и (б).

**Сериализация** — часть инварианта, а не рекомендация реализации.
Любая операция, меняющая статус обращения или его задачи — переход,
создание, выполнение, отмена, передача задачи, — блокирует строку
обращения и целиком выполняется в одной транзакции. Поэтому создание
новой задачи не может произойти между закрытием обращения и отменой
его задач и обойти И16.

### 5.7 Эскалация и возврат (И17)

Переход ESCALATED → S, где S — статус, из которого пришли:

| | |
|---|---|
| Меняется | только `status` := S и `status_before_escalation` := пусто |
| Добавляется | ровно одно событие `status_changed` |
| Не меняется | номер и счётчик номеров; вехи `opened_at` … `closed_at`; `suggested_route`, `final_route`, `route_changed_by`, `route_change_reason`; `assigned_to`, `priority`, `urgency`, `legal_basis` |
| Не создаётся | направлений, исходов, задач, снимков согласия, версий анкеты |

Вход в ESCALATED меняет только `status` и `status_before_escalation`,
причина обязательна, событие — одно. Последствия перехода в статус S
выполняются один раз — когда обращение впервые туда пришло, — и при
возврате не повторяются.

## 6. Экстренность, приоритет, сроки

**P0 — клиническая экстренность.** Бот уже сейчас сразу говорит
звонить 103/112 (распознавание в свободном тексте и тревоги анкеты).
Для службы P0 значит: обращение сразу `NEW`, уведомление старшему
и координатору, перезвонить после того, как острое состояние
разрешилось.

**P1–P3 — приоритет службы.** Ниже — заготовка, **не решение**:
правила утверждает служба регламентом.

| Приоритет | Заготовка признаков | Срок реакции — предложение |
|---|---|---|
| P1 | тревоги «кожа» (открытая рана), «глотание»; маршрут М1; «ухаживать некому» при утрате 3+ параметров | ? |
| P2 | маршрут М5; «на пределе / не справляемся» | ? |
| P3 | остальное, навигационные вопросы | ? |

Приоритет, посчитанный по правилам, хранит версию правил и сигналы
(И6). Приоритет, выставленный координатором вручную, — с причиной и
без версии правил (Ч10).

**Срок реакции** считается по рабочему календарю службы: часы
работы, выходные, праздники. Обращение, пришедшее в субботу в 23:00,
получает срок от начала следующего рабочего периода — если служба
не решит иначе для P0/P1 (дежурство). Обещать «2 часа», не имея
дежурного, нельзя.

## 7. Когда создаётся обращение

1. **До согласия обращения нет.** Единственное исключение —
   режим Б, и только если служба его утвердит (Р10). Пока Р10 не
   принято, бот к модели обращений не подключается (раздел 14).
   **Р10 решено службой: режим А** (раздел 12) — бот подключён к
   модели обращений (шаг 2) и действует по режиму А ниже.

   **Режим А — по умолчанию.** Признак угрозы жизни до согласия живёт
   только во время обработки сообщения. Человек сразу получает
   103/112; в метрики (`metrics.py`) уходит счётчик срабатываний по
   группе признака — без идентификатора человека и без текста. В
   состояние разговора и в CRM не пишется ничего. Нынешнее поведение
   (Д9) убирается, и координатор такого человека не увидит — в этом
   и цена режима.

   **Режим Б — исключение по п. 3 ч. 2 ст. 10 ФЗ-152** (защита жизни,
   когда согласие получить невозможно). Включается только письменным
   решением службы с юристом. Создаётся обращение сразу в `NEW` с
   номером, `urgency = P0`, `legal_basis = vital_interest`. Хранится
   минимум: идентификатор канала, группа признака (в тревогах анкеты
   версии 1, Ч8), время — ни текста сообщения, ни ответов. Координатор видит такое обращение первым и
   может написать человеку в чат. Дал человек потом согласие — снимок
   согласия добавляется к этому же обращению, `legal_basis`
   становится `consent`. Не дал — после разговора координатор
   закрывает обращение с причиной `consent_not_given` (5.3), и оно
   удаляется через срок из Р10.
2. **Согласие дано → обращение `DRAFT`**, снимок согласия (4.3) и
   intake версии 1. Номера у черновика нет.
3. **Все ответы, сообщения, рассказ и тревоги дальше относятся
   к нему.** «Продолжить подробную анкету» — то же обращение и та же
   версия intake.
4. **`DRAFT → NEW`** по первому из трёх оснований раздела 5.2 (Ч7).
   Номер (4.9) и уведомление координатору — в той же транзакции.
5. **«Заново» / «начать», пока обращение открыто** — не новое
   обращение, а новая версия intake в том же обращении, на том же
   согласии; координатор видит «анкета заполнена заново» и обе версии.
6. **Новое обращение — только после `CLOSED`, и с новым согласием**
   (одно нажатие). Согласие дано ради конкретного обращения: его цель
   («чтобы координатор перезвонил, понял, что нужно, и подобрал
   помощь») достигнута закрытием. Если координатор увидит, что новое
   обращение о том же, он закрывает его как `duplicate`.
7. **Черновик, не ставший `NEW` за 30 дней,** закрывается как
   `abandoned_draft` и удаляется. Срок предлагается и попадёт в текст
   согласия только после Р5 (Д10).
8. **Идемпотентность.** Создание обращения происходит в той же
   транзакции, что обработка события MAX (`processed_events`), и
   защищено уникальным частичным индексом «одно открытое обращение
   на человека и канал». Повторная доставка того же события второго
   обращения не создаст.

## 8. Сроки хранения

Срок хранения обращения определяется согласием, на котором оно
держится (4.3), и статусом. Пока Р5 не принято, таблица ниже —
предложение, а не обещание: подписанное согласие 1.0 срока не
называет вовсе (Д10).

| Что | Срок | Затем |
|---|---|---|
| `DRAFT`, не ставший `NEW` | 30 дней | удаляется целиком |
| Открытое обращение | до закрытия | — |
| Закрытое обращение | 1 год полностью; дальше — Р5 | обезличить сразу или держать до 3 лет; после — только обезличенная статистика |
| Режим Б без согласия | срок из Р10 | удаляется целиком |
| Журнал доступа операторов | свой срок | ротация |

После Р5 одна таблица сроков переносится сразу в три места: текст
согласия 1.1 (через юриста), статью базы и скрипт удаления. Тест
сверяет все три, чтобы Д10 не повторился.

Удаление по просьбе человека затрагивает все его обращения и все
новые таблицы; это проверяется тестом на каждую таблицу.

## 9. Уведомления и сообщения человеку

Координатору и старшему в MAX: `SDUT-2026-00124 · P2 · Автозаводский
район · реакция до 17:00 · ссылка в CRM`. Без имени, диагноза,
ответов. Отдельно: просрочка задачи → старшему; P0 → сразу обоим.

### 9.1 Автоматические сообщения после смерти (И18)

Виды исходящих сообщений человеку:
- ответ бота на сообщение человека;
- сообщение координатора, написанное вручную;
- **автоматическое** — инициированное системой без входящего
  сообщения человека: напоминание, опрос, рассылка.

Сейчас автоматических сообщений нет вовсе. Правило — на будущее,
чтобы их нельзя было добавить без него.

**После закрытия по `ward_died` семье не уходит ни одного
автоматического сообщения:**

(а) Переход в CLOSED(`ward_died`) в той же транзакции отменяет все
ещё не взятые на отправку автоматические сообщения этому человеку.
(б) После фиксации такого закрытия очередь не берёт на отправку ни
одного автоматического сообщения этому человеку.
(в) Сообщение, взятое на отправку до фиксации, — предмет правила
очереди исходящих (9.2). Итог: каждое автоматическое сообщение либо
отправлено до фиксации закрытия, либо не отправлено вовсе.
Отправленное до фиксации отозвать нельзя — это честная граница.
(г) Ответы бота на сообщения самого человека и сообщения координатора
не запрещены: если родственник пишет, бот не должен молчать.
(д) Если человек сам начнёт новое обращение, автоматические сообщения
разрешаются только в контексте нового обращения. Закрытое по
`ward_died` обращение не возобновляется и не служит контекстом
нового; сообщения, отменённые при его закрытии, не восстанавливаются
и не отправляются; новое обращение не «размораживает» старую очередь.

### 9.2 Правило очереди исходящих (шаг 2)

Защита от гонки «сообщение взято из очереди → обращение закрыто или
данные человека удалены → сообщение всё равно ушло» — не доменная
логика обращения, а отдельное инфраструктурное правило очереди
исходящих. Оно оформляется на шаге 2 и применяется ко всем основаниям
запрета отправки: к закрытию по `ward_died` (9.1) и к удалению данных
по просьбе человека.

Суть правила: перед необратимым внешним действием — вызовом MAX —
отправитель под блокировкой строки сообщения ещё раз проверяет, что
право на отправку не отозвано; транзакция, отзывающая право, отменяет
сообщения под той же блокировкой.

Сейчас для удаления данных есть только проверка при взятии сообщения
на отправку (`deleted_users` в `outbox_postgres.claim`); перепроверки
перед вызовом MAX нет — сообщение, взятое за миг до удаления, уйдёт.
До шага 2 `outbox_postgres.py` не меняется.

## 10. Хранилища

Доменная модель от хранилища не зависит. Правила — в модуле
обращений, хранилище — за интерфейсом репозитория:

```
        модуль обращений: правила, переходы, номера, сроки
                              │
                    интерфейс репозитория
            ┌─────────────────┼──────────────────┐
       PostgreSQL           SQLite             память
     круглосуточно     пилот на ноутбуке   модульные тесты
                       (только если Р6)
```

У адаптеров нет своей бизнес-логики — только чтение и запись.
Поэтому один и тот же набор тестов контракта прогоняется на каждом
адаптере. PostgreSQL — хранилище круглосуточной работы. SQLite
допускается только как адаптер локального пилота, если Р6 оставляет
ноутбук. JSON-CRM (`crm_store.py`) удаляется: это не адаптер, а
вторая бизнес-модель (Д5). Файловый режим разработки переходит на
адаптер в памяти или SQLite.

## 11. Перенос текущих данных

Миграция `014_cases` и одноразовый перенос; повторный запуск
безопасен. Принцип — раздел 3, п. 5: чего тогда не сохранили, того
задним числом не выдумываем.

| Было | Стало |
|---|---|
| строка `survey_state` | `person` + `case` + `intake` v1 |
| `survey_state.consent = {at, version}` | `case_consents`: `processing`, версия из записи, `given_at = at`, `text_hash` пусто — текст на момент согласия не сохранялся; `medical_transfer` — только если координатор отметил подписанную форму |
| `operator_cases.status = Новое` | `NEW` (или `DRAFT`, если контрольная точка не пройдена) |
| `В работе` | `ASSIGNED`, если есть `assigned`, иначе `NEW` |
| `Закрыто` | `CLOSED`, `close_reason = migrated` |
| номер | обращениям `NEW` и дальше — по порядку `started`, год по `started` в местном времени; черновикам — нет; счётчик года выставляется на последний выданный |
| `operator_notes` | `case_events` |
| `operator_calls` | задачи `control_d7` / `control_d30` в статусе `done` |
| маршрут | `suggested_route` пусто: старый бот маршрут не сохранял, исторического факта нет. Реконструкция по текущим правилам — отдельное событие `route_reconstructed {route, also, signals, rules_version, calculated_at}`. CRM подписывает её «восстановлено при переносе», и в сравнение «бот предложил / координатор решил» такие обращения не входят |

Старые таблицы остаются только для чтения на один выпуск и затем
удаляются. Проверка переноса — на копии реальной базы.

**Проверка каждого шага.** Репозиторий — форк, и GitHub не запускает

локально тесты PostgreSQL без базы пропускаются, и сломанная
миграция видна только в CI.

с результатом, ни одна задача не осталась без срока и исполнителя,
а отчёт показывает все три уровня.
