# Модель обращения — шаг 1: соответствие контракту

**Контракт:** `docs/МОДЕЛЬ-ОБРАЩЕНИЯ.md`, редакция 2 (доменный контракт v1,
утверждён). Этот документ — шаг 0 из раздела 14: каждое правило →
файл → тест. Правила здесь не меняются; где контракт молчит или
допускает два прочтения, это вынесено в разделы «Прочтения» и
«Пробелы» и ждёт подтверждения в редакции 3.

**Объём шага 1:** модуль обращений, интерфейс хранилища, адаптеры
памяти и PostgreSQL, миграция 014, тесты контракта. Бот, CRM, перенос
данных и сроки по календарю не подключаются — это шаги 2–6.

Тест `tests/test_cases_mapping.py` сверяет этот документ с кодом:
каждый тест из таблиц существует, у каждого инварианта И1–И15 есть
тест с его номером в имени.

и обратимое; на подтверждение в редакции 3.

| № | Место | Прочтение |
|---|---|---|
| Ч1 | 4.1 и И14 | После удаления по просьбе строка `persons` остаётся отметкой удаления (4.1 прямо задаёт `deleted_at`): канал, идентификатор, время удаления. Всё остальное стирается. Вернувшийся человек проходит как новый — `deleted_at` снимается |

## Пробелы — вопросы к редакции 3

Здесь контракт не даёт правила или противоречит сам себе. Код ничего
не додумывает: операция отклоняется с ошибкой `ContractGap`, либо
поведение остаётся ручным. Отклонение проверяют
`test_г1_продление_контроля_ждёт_редакции_3` и
`test_г5_эскалация_черновика_ждёт_редакции_3`.

| № | Пробел | Что сейчас в коде | Предложение |
|---|---|---|---|
| Г1 | CONTROL → CONTROL «новая контрольная задача с причиной»: вид задачи не определён — `control_d7`/`control_d30` считаются от начала помощи | переход отклоняется `ContractGap` | новый вид `control_extra`, срок указывает координатор |
| Г2 | Нет закрытия после разговора, если помощь уже не нужна или человек отказался: из CONTACTED в CLOSED пути нет, приходится подтверждать маршрут ради закрытия. Режиму Б без согласия причина закрытия тоже не назначена | только переходы таблицы 5.2 | заменено проектом редакции 3 (`docs/МОДЕЛЬ-ОБРАЩЕНИЯ-Р3-ПРОЕКТ.md`, Г2): `consent_not_given` — только из CONTACTED при `vital_interest` |
| Г3 | Нет причины закрытия «подопечный умер». Для этих людей — частый исход, и записывать его как `refused` или `solved_otherwise` — искажение статистики | причины только из 5.3 | `ward_died` |
| Г4 | Что с открытыми задачами, когда обращение закрывают или уводят из CONTROL на новое направление | задачи остаются открытыми, координатор отменяет вручную (`cancel_task`) | закрытие обращения отменяет его открытые задачи; уход из CONTROL отменяет открытые контрольные — новые создаст следующий вход в CONTROL |
| Г5 | Эскалация черновика: 5.2 разрешает ESCALATED из любого открытого статуса (Ч5 — включая DRAFT), а И2 и 4.9 требуют номер у каждого рабочего обращения; у черновика номера нет. Противоречие нашла база: ограничение `cases_working_has_number_ck` | переход DRAFT → ESCALATED отклоняется `ContractGap` | эскалировать и объединять только то, что видит координатор, — без DRAFT (5.1: черновик в очереди CRM не виден) |
