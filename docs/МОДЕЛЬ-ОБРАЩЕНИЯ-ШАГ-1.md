# Модель обращения — шаг 1: соответствие контракту

**Контракт:** `docs/МОДЕЛЬ-ОБРАЩЕНИЯ.md`. Шаг 1 реализует редакцию 2
(доменный контракт v1, утверждён). Этот документ — шаг 0 из раздела
14: каждое правило → файл → тест. Правила здесь не меняются; где
контракт молчит или допускает два прочтения, это вынесено в разделы
«Прочтения» и «Пробелы».

**Редакция 3** контракта утверждена и реализована: модуль обращений,
оба хранилища, миграция 015, тесты. Она решила пробелы Г1–Г5 и
утвердила прочтения Ч1–Ч12; её соответствие коду и тестам — раздел
«Редакция 3» в конце, инварианты И1–И18 — таблица «Инварианты →
тесты». И18 и правило очереди 9.2 реализованы на шаге 2 — вместе с
подключением MAX → CASE → CRM (PR #3), раздел «Шаг 2» в конце.

**Объём шага 1:** модуль обращений, интерфейс хранилища, адаптеры
памяти и PostgreSQL, миграция 014, тесты контракта. Бот, CRM, перенос
данных и сроки по календарю не подключаются — это шаги 2–6.

Тест `tests/test_cases_mapping.py` сверяет этот документ с контрактом и
кодом: инварианты берутся из контракта, у каждого здесь либо есть тест
с его номером в имени, либо явный TODO; каждый названный тест
существует. TODO — не реализация: такие инварианты он перечисляет в
предупреждении на каждом прогоне.

и обратимое. Утверждённая редакция Ч1–Ч12 — в контракте, раздел 16;

## Пробелы — вопросы к редакции 3

Здесь контракт не даёт правила или противоречит сам себе. Код ничего
не додумывает: операция отклоняется с ошибкой `ContractGap`, либо
